# kb.py 通俗讲解：知识库是"图书馆"，不是"文件柜"

> 用大白话讲清楚 `backend/app/kb.py` 为什么这么设计，以及每个零件将来在项目里干什么。
> 读完这篇，面试被问"你的 RAG 是怎么做的"时，你能用这套类比讲 3 分钟。

## 一、先记住一句话

> **kb.py 是给项目建的一座"语义图书馆"：把零散的文字存进去，以后能按"意思"把它找出来。**

注意是"按意思"找，不是"按关键词"找。搜"猫"能找到写"喵星人"的段落——因为存储时文字被翻译成了机器能比对的"向量"（一串数字）。向量就是每段文字的"语义指纹"。

## 二、图书馆类比（整个文件的骨架）

| 代码里的东西 | 类比 | 说明 |
|---|---|---|
| `vault/.kb/chroma_db` | 图书馆的仓库 | 向量和原文都存在这里的 sqlite3 文件里 |
| `get_collection()` | 图书馆管理员 | 全馆只有一个，随叫随到（懒加载单例） |
| `OpenAIEmbeddings` | 翻译官 | 把中文/英文翻译成 1024 维向量 |
| `RecursiveCharacterTextSplitter` | 装订工 | 把长文裁成 500 字左右的"卡片" |
| `upsert_document` | 存书员 | 把卡片放进仓库（先清掉旧卡片再放新的） |
| `retrieve` | 查书员 | 拿"问题"去仓库里找意思最接近的卡片 |
| `delete_document` | 撤书员 | 把某个文档的所有卡片撤走 |
| `extract_pdf_pages` | 拆书工 | 把 PDF 一页一页拆开 |
| CLI（`python -m app.kb ...`） | 自助查询台 | 不打开网页也能存书查书（调试用） |

## 三、每个设计决策的大白话解释

### 1. 为什么要"分块"（500 字一块）？

大模型一次只能看有限的文字（上下文窗口）。一篇 10 页论文塞不进去，但"第 3 页的 500 字"塞得进去。所以**把长文裁成卡片**，检索时只挑最相关的几张卡片给模型看。

为什么 500 字？太短（50 字）——意思不完整，模型看不懂；太长（5000 字）——废话太多，检索不精准。500 是经验值。为什么留 50 字重叠？**接缝不断裂**——卡片 A 结尾和卡片 B 开头重叠一点，句子不会被"腰斩"。

为什么分隔符要加中文标点？英文靠空格分词，中文不靠——如果不加 `。！？；，`，中文句子可能在半句话的地方被硬切。加了之后，切块的边界尽量落在句号上，每张卡片都是"完整的话"。

### 2. 为什么要"页级分块"（每页单独切）？

因为**回答要能说出处页码**（PRD 要求"回答附来源：文献名+页码"）。如果卡片跨页，就不知道它属于第几页。所以每页单独切，卡片上钉个"页码"标签（`metadata.page`）。代价是每页末尾的卡片可能不满 500 字——为了页码准确，值得。

### 3. 为什么 upsert 要"先删旧的再存新的"？

这叫**幂等**（idempotent）：同一个文档存 10 次，结果和存 1 次一样。如果不先删，文档改一版再存一次，仓库里就有新旧两套卡片，检索时同一个内容会出现两份。

这在 B6（自动扫描 vault）时特别重要——扫描可能反复跑，每跑一次必须结果一致，不能越扫越多。

### 4. 为什么要"翻译官"（embedding）？它怎么翻译的？

embedding 模型（这里是 bge-m3）把"一句话"变成 1024 个数字。**意思相近的句子，数字串也相近**。检索时，把问题也变成向量，然后算"哪个卡片的向量离问题向量最近"——最近的几张就是"最相关"的。

### 5. 为什么"管理员"只有一个（懒加载单例）？

`get_collection()` 第一次被调用时才开门（连接 Chroma 数据库），之后永远返回同一个实例。好处：不浪费资源（连接只建一次），而且全项目共享同一本"目录"。

为什么叫"懒"？因为**用到了才建**。如果项目跑起来但没人查书，就不用白白启动翻译官和管理员。

### 6. 为什么整文件是同步的，不做 async？

langchain 的 embedding 和 Chroma 只提供"同步"版本（执行完才返回）。kb.py 就老实写成同步。将来在 async 路由（B5/B7）里调用时，用 `anyio.to_thread` 把它丢到后台线程执行——**像点外卖：骑手去取餐，你在家继续干别的，餐到了再签收**。事件循环不被卡住。

为什么不硬写成 async？因为核心本身没有异步能力，包装成 async 是"假 async"，误导人。谁调用、怎么调度，由调用方决定（见 ADR-0002）。

### 7. 为什么没配 API key 就直接报错？

`_get_embeddings()` 发现 `SILICONFLOW_API_KEY` 是空的，**当场抛错**，不装聋作哑。这是"明确失败优于静默失败"——翻译官没有钥匙，存书必然失败，与其藏着掖着让后续一堆怪问题，不如一开始就告诉你"钥匙没配"。

（B7 的"降级"是另一回事：检索失败时 AI 降级为不带知识库的普通对话，那是**调用方**的容错策略，不是这里的静默。）

### 8. 为什么 .kb 可以随便删？

vault 里的 `.md` 和 `.pdf` 是**原始数据**（你的资产，进云盘、进 Git）；`.kb/chroma_db` 是**派生数据**（图书馆的目录和卡片，可以从原始数据重新生成）。派生数据坏了不用慌——删掉，让 B6 重新扫描一遍，图书馆重建完毕。这就是"原始数据 vs 派生数据"分层，面试说出这一点很加分。

## 四、每个零件将来在项目里的用场（对应 WBS）

| 零件 | 将来谁用 | 干什么 |
|---|---|---|
| `extract_pdf_pages` | **B5**（导入文献）、**B6**（扫描 vault） | 导入 PDF 后抽文本建索引 |
| `split_pages` | 被 `upsert_document` 内部调用 | 笔记和 PDF 都走它切块 |
| `upsert_document` | **B5**（导入后索引）、**B6**（全量/增量扫描）、**F2**（笔记保存后索引） | 新文档进图书馆 |
| `delete_document` | **B5**（删除文献）、**F3**（删除笔记） | 文档删除后清理索引，防止"幽灵引用" |
| `retrieve` | **B7**（RAG 问答，用户亲手写注入逻辑） | 全局问答 / 单篇问答的检索核心 |
| `get_collection` | 上面所有函数的公共入口 | 管理员 |
| `_default_vault_path` / `_kb_root` / `_chroma_dir` | B4（文件 API 的安全边界也要用 vault 路径） | 决定"东西放哪" |
| CLI | 开发调试 + 面试 demo | 不启动网页也能演示"存→查→删"全流程 |

## 五、面试怎么答"介绍一下你的 kb.py"

> "kb.py 是我们的 RAG 知识库核心，职责是三个：**存、删、查**。
> 存：文档文本（笔记或 PDF 逐页抽取）经过 500/50 的中文分块，转成 bge-m3 向量，幂等写入 Chroma，持久化在 vault/.kb 下；
> 删：按 docId 精确清理，文档删除时同步清理索引；
> 查：相似度检索，支持全局检索和按 docId 限定单篇（问答面板的全局/单篇两种模式复用同一函数，区别只在过滤条件）。
> 几个关键设计：页级分块保证来源页码准确；.kb 是派生数据可删可重建；核心同步、async 路由用 to_thread 调度。"

说完可以补一句："检索注入（怎么把结果拼进 prompt）是 B7 我自己手写的部分，这里只提供查询能力"——展示你对模块边界的清楚认知。

## 六、面试官可能的追问（预演）

- **"为什么不用关键词搜索（BM25）而用向量检索？"** → 语义检索能命中"同义不同词"；BM25 是词面匹配。生产系统两者常结合（hybrid），MVP 先上向量。
- **"向量怎么比较相似度？"** → 余弦相似度（或内积），Chroma 默认计算；距离越小越相关。
- **"如果 embedding 服务挂了怎么办？"** → B7 设计降级：检索失败 → 不带知识库的普通对话，SSE 协议不变。
- **"为什么不用 Elasticsearch？"** → 单机本地优先，Chroma 是嵌入式向量库（一个目录一个文件），零运维，符合"无数据库"架构；ES 是分布式服务，重。
