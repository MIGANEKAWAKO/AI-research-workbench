# 面试问答积累

> 按五类持续积累：①技术选型 ②核心机制 ③设计权衡 ④踩坑经历 ⑤原理深挖。每完成一个模块补充条目。

## ① 技术选型

### Q1：为什么 LangChain 拆包安装，不装 langchain 大包？
**答**：langchain 0.3+ 官方拆包架构，核心抽象在 `langchain-core`，各集成（openai/chroma/community...）独立成包。本项目只需要检索侧的 4 件事：embedding（langchain-openai）、分块（langchain-text-splitters）、向量库（langchain-chroma）、核心抽象（langchain-core）。装大包会拖入几十个用不到的集成（anthropic、cohere、ai21...），安装体积大、依赖冲突风险高。按需引入、控制依赖面，是长期维护的核心原则。

### Q2：为什么 embedding 用 SiliconFlow 的 BAAI/bge-m3？
**答**：三个原因。① DeepSeek 不提供 embedding 接口，需要独立的 embedding 服务；② bge-m3 是中文场景效果好的开源 embedding 模型，SiliconFlow 提供便宜的 API 托管；③ SiliconFlow 提供 OpenAI 兼容协议（`/v1`），可以复用现有 openai SDK，不引入新客户端。（对应架构决策 ADR：RAG embedding 选型）

### Q3：元数据补全的 HTTP 客户端为什么用 httpx 不用 requests？
**答**：httpx 是异步客户端，支持 `AsyncClient` + `async with`，在 FastAPI 的 async 事件循环里不阻塞其他请求；requests 是同步阻塞库，如果在 async 路由里直接调用，会卡住整个事件循环（其他用户请求排队等 I/O）。此外 httpx 原生支持 HTTP/2、连接复用，也是 starlette/openai SDK 生态的标准选择。注意一个 httpx 和 requests 的默认行为差异：**httpx 默认不跟随重定向**（`follow_redirects=False`），requests 默认跟随——这点踩过坑，见踩坑记录。

### Q4：为什么不用 langchain-deepseek / langchain-community 接入 DeepSeek？
**答**：因为 LLM 层根本没进 LangChain。DeepSeek 是 OpenAI 兼容协议，现有代码直接用 openai SDK 直连（AsyncOpenAI + base_url 指向 DeepSeek），链路已通。LangChain 在本项目只承担检索侧（embedding/分块/向量库），LLM 调用走现有 SSE 中转，协议逐字节不变。langchain-deepseek 和 community 里的 DeepSeek 封装本质都是把 ChatOpenAI 包一层 base_url，对这个场景是纯增本。

### Q5：前端存储为什么做 StorageAdapter 抽象？为什么接口先行？
**答**：开发期（浏览器）和发布期（Tauri）的文件系统实现完全不同——浏览器只能走后端 HTTP 兜底（`/api/fs/*`），Tauri 有原生 fs 插件。如果业务代码直接 fetch 后端，发布期换 Tauri 时所有调用点都要改；抽象成 `StorageAdapter` 接口后，业务只依赖抽象，工厂 `createStorageAdapter()` 一处切换实现。这就是**依赖倒置原则（DIP）**：高层模块（业务）不依赖低层模块（具体文件系统），双方都依赖抽象。接口先行（先定 6 个方法签名再写实现）让前后端可以并行开发——B4 未完成时可以用 mock 实现调试 UI。

### Q6：笔记为什么用 Markdown + YAML frontmatter，而不是纯 HTML 或 JSON 文件？
**答**：产品定位决定（PRD 5.2）——vault 文件是用户资产，要能被 Obsidian / VS Code / Git / 云盘直接使用。① Markdown 通用可读，任何编辑器能打开；HTML 是渲染层格式，人眼不可读；JSON 结构好但 Obsidian 生态不认。② frontmatter 是 Obsidian 生态的元数据惯例（YAML 头），内容和元数据同文件，文件自包含（拷走一个 .md 就带着标题/标签/引用信息）。③ 数据与显示分离：存 Markdown 源文本，渲染由编辑器决定。代价：Markdown 表达力弱于 HTML（背景色等视觉信息会丢），这是**内容优先于排版**的取舍。

### Q7：为什么文献库用"侧边栏 Tab 切换"而不是引入路由？
**答**：项目在依赖清理时移除了 react-router-dom（无多页面需求）。F4 只需要两个视图（笔记/文献）的切换，一个 `view: 'notes' | 'library'` state（放 useNoteStore，SiderBar 与 Home 共享）即可——比路由更轻：无 URL 语义、无懒加载需求、状态切换即时。什么时候该上路由？① 视图可深度链接（URL 即状态，如详情页分享/刷新保持）；② 独立页面数 >3；③ 需要路由级懒加载。面试可展开"路由的本质是 URL 与 UI 状态的绑定，没有这个需求就不引入复杂度"（YAGNI 的又一实例）。

## ② 核心机制

### Q1：项目的配置加载机制是怎样的？
**答**：`backend/app/config.py` 用 dataclass + dotenv。启动时 `load_dotenv()` 读 `.env` 文件，Settings 是 frozen dataclass，每个字段默认值直接取 `os.getenv(...)`，没有配置时用代码里的默认值（如 deepseek_base_url、embedding_model）。整个应用共享一个 `settings` 单例（模块级实例化），各模块 `from .config import settings` 使用。关键点：.env 不入 git（.gitignore），`.env.example` 是模板。

### Q2：前端 useDataStore 的"内存缓存 + 文件持久化"双层结构是怎么工作的？
**答**：`useDataStore`（Zustand）仍是唯一的响应式数据源，UI 组件只订阅内存状态（行为与原来的 useLiveQuery 等价）；持久化发生在 actions 内部——`loadAll` 扫描 `vault/笔记/*.md` 逐个读入内存（应用启动时调用一次），`saveNote` 写文件 + 更新内存，`deleteNote` 删文件 + 更新内存。这样 UI 层完全不知道文件系统的存在。面试可以追问：**为什么保留内存缓存而不直接每次读文件？** 因为 React 需要同步可读的状态做渲染，读文件是异步的；内存缓存 = 读时异步加载、写时同步更新，是"读写分离"的常见模式（类似 SWR/React Query 的 cache-first）。

### Q3：笔记 title 为什么是"双源"的？frontmatter 和文件名谁说了算？
**答**：frontmatter.title 优先、文件名为 fallback。两个来源都有意义：frontmatter 是权威元数据（Obsidian 显示它、后端索引它），文件名是存储标识（F1 定死、不随编辑变化）。F3 起 title 权威化：编辑器自动保存**不再**用正文第一行覆盖 title（否则侧边栏重命名会被下次编辑覆盖），title 只由新建/重命名决定；文件名保持新建时的值。读取时：frontmatter 有 title 用 frontmatter 的，没有（F1 遗留的无 frontmatter 旧文件）回退文件名。面试加分：双源设计解决"用户可改标题（frontmatter）"与"存储路径稳定（文件名）"两个需求的冲突，F6 引用系统引用的也是 frontmatter title。

### Q4：30s 轮询为什么用 `refreshFromDisk(skipNoteId)` 而不是直接 `loadAll` 覆盖？
**答**：直接全量覆盖有一个数据丢失窗口：用户正在输入时（自动保存 600ms 防抖窗口内），磁盘还是旧内容——轮询若把内存 notes 覆盖成旧版，用户切换笔记时会读到旧内容，刚输入的内容就丢了。方案：轮询全量重读，但**跳过正在编辑的笔记**（skipNoteId = 当前 activeNoteId，保留内存值）。为什么不担心该笔记最终不一致？① 编辑器 doc 状态独立于内存 notes，自动保存最终会把内容写回磁盘；② 该笔记不再编辑后，下一次轮询（30s 内）就会以磁盘为准更新。这是"轮询兜底"的最小正确实现——保护写窗口、其余全量同步。面试追问"为什么用轮询不用监听"：开发期后端无推送链路（PRD 决策：后端直接读 vault，无前端推送同步），30s 轮询是 PRD 8.4 指定的轻量方案，M2 换 watchdog + SSE。

### Q5：文献库数据为什么没有"内存缓存 + 文件真源"双层？和笔记的存储架构区别在哪？
**答**：笔记的真源是 vault 里的 .md 文件（用户资产，前端直接读写，所以需要内存缓存做响应式渲染 + StorageAdapter 持久化）；**文献元数据的真源是后端的 literature.json**（后端管理：导入写盘、索引、重复检测都在后端），前端是纯消费者——每次进入文献模式 `load()` 拉取，操作后本地更新内存即可。如果前端也缓存文献，就要处理"前端缓存 vs 后端真源"的一致性（谁来写？冲突怎么办？）——**数据只有一个写者时最不需要缓存层**。面试加分：缓存层是为"读写分离"服务的，当读路径已经足够快（本地后端）且写路径完全在后端时，缓存的收益小于一致性成本。

### Q6：导入时自动提取 DOI 是怎么设计的？（B5.1）
**答**：补全机制的钥匙是标识符——用户不填就查不了。自动提取把"钥匙"从用户手里拿过来：导入不带 identifier 时，用 B6 已有的 `extract_pdf_pages` 抽文本（本来建索引也要抽），正则从**前 2 页**匹配 DOI（首页必有），找到就调 Crossref 补全；抽取结果缓存复用给索引，不重复抽。三个设计细节：①**显式 > 自动**——用户填了 DOI/arXiv 就绝不自动提取；②**正则分层**——先匹配精确形态（`doi.org/`、`doi:` 前缀）再裸 `10.xxxx/`（负向后顾 `(?<![\w.])` 防把超链接/数字串误判成 DOI），字符集限定排除空白和中文防贪婪，尾部 rstrip 标点（PDF 里 "…130053." 的句号不能吞进 DOI）；③**失败降级**——假 PDF/扫描件抽不出文本就保持 title 占位，不阻断导入（延续 B2/B5 的降级约定）。面试加分：这是"减少用户必须知道的内情"的体验设计——元数据补全不该要求用户理解 DOI 机制。

## ③ 设计权衡

### Q1：dataclass + dotenv vs pydantic-settings，为什么选前者？
**答**：现状一致优先——现有 3 个字段就是 dataclass 模式，扩展 5 个字段保持一致，零新依赖。pydantic-settings 的优势（类型校验、嵌套配置、自动转换）在配置变复杂时再迁移。注意这次装依赖时 pydantic-settings 作为 chromadb 的传递依赖被装进来了，但**我们没直接用它**——这是"间接依赖"和"直接依赖"的区别，面试时可以说清楚。

### Q2：版本约束为什么用 `>=x,<y` 而不是 `==x.y.z`？
**答**：语义化版本区间。`>=x,<y` 让 pip 在解析时自动选择兼容的最新版本，与现有依赖（fastapi、openai）协同解析不冲突；pin 死版本则维护成本高、升级要手动改。代价是可复现性不如锁文件（poetry.lock/pip-tools），单机个人项目取可升级性，团队项目才需要锁文件。

### Q3：为什么检索要支持"单篇限定"（where 过滤）？Chroma 的过滤是怎么实现的？
**答**：产品需求决定的——AI 面板有两种模式：全局问答（整个知识库检索）和单篇问答（只看当前文献，PRD 4.6）。两种模式复用同一个检索函数，区别只在过滤条件：全局不带 filter，单篇传 `filter={"docId": doc_id}`。Chroma 的过滤在**向量检索阶段**应用（先在元数据上过滤出候选集合，再在候选内做相似度排序），不是检索后丢弃——所以单篇检索不会"漏掉"相关块，而是精确限定范围。面试可深挖：where 过滤的字段必须是基础类型（str/int），不能存复杂对象，这就是为什么元数据只有 docType/docId/page/title。

### Q4：文献作者为什么存结构化 `[{given, family}]`，不存 "John Smith" 字符串？
**答**：为导出格式化（B8）铺路。GB/T 7714 要求西文作者"姓 全大写 + 名缩写"（如 SMITH J.），APA 要求"Smith, J."——格式化的前提是**姓名有边界**（哪个词是姓）。存字符串就只能盲猜 split（"John Smith" 还好，"Van der Berg" 这种复姓必错）。Crossref API 直接返回 given/family 字段，arXiv 返回名字字符串，解析时"最后一个 token 视为 family"；机构作者（如 "Google Research"）放 family。这就是 PRD 4.5 的**数据与格式分层**：只存结构化元数据，格式化是导出时的纯函数。

### Q4：为什么 VAULT_PATH 只留配置位不拍板默认值？
**答**：vault 是用户自选文件夹，默认值的推导要和前端首次启动引导流程联动（F1 阶段）。现在定死默认值属于过度设计——把决策推迟到真正需要它的模块（B3/B4），配置位先铺好，接口不变，后续填实现即可。

### Q5：为什么 saveNote 保持同步签名（fire-and-forget 写文件）？改成 async 不行吗？
**答**：对外 API 稳定性优先。`saveNote: (note) => number` 的调用方有编辑器 600ms 防抖保存、SiderBar 新建笔记——改成 async 所有调用点都要加 await，违背 F1"UI 零改动"目标。方案：**内存更新同步完成**（Zustand set 立即生效，UI 响应式刷新），**文件写入异步执行**（adapter.write 后接 .catch 记日志，不阻塞调用方）。代价：极端情况下（后端挂、磁盘满）写失败用户无感知，刷新后数据丢失——这是接受的权衡，F2 可加写队列 + 失败提示。面试追问：为什么不直接 await？因为防抖回调本身就是 async，await 一个写入没问题，问题在于**新建路径**——SiderBar 要同步拿到新 id 才能 setActiveNote 跳转，而 id 分配和文件写入解耦后，同步分配 id、异步写文件是最小改动方案。

### Q6：笔记文件名为什么在新建时定死，不随标题变化？
**答**：读了 editor 调用点发现一个关键事实：自动保存会把 title 改成正文第一行（`firstLine.slice(0, 30) || 'Untitled'`）——**title 是动态值**。若文件名 = title，每次改首行笔记就"搬家"（删旧文件建新文件），且两篇同标题笔记会互相覆盖。所以 F1 约定：文件名在新建时按当时的标题确定（重名自动加 ` (2)` 后缀），此后 title 变化只更新内存。F2 引入 frontmatter 后，文件内 title 字段是权威元数据、文件名只是存储标识，这个问题从根上消失。这个决策的教训是：**接口签名不变 ≠ 调用行为不变**，改造前必须读调用方代码。

### Q7：为什么 collection 在 frontmatter 里存名字符串，内存里却用数字 id？双 id 体系不冗余吗？
**答**：两个 id 服务不同目的。文件里存 `collection: 论文笔记`（名字）：人类可读、Obsidian 兼容、文件自包含（换机器/换工具不丢归属语义）；内存里用数字 id：React 渲染 key、拖拽/过滤比较都要求稳定且高效的标识，字符串比较/中文名当 key 既不优雅也容易出错。useDataStore 内部做 name↔id 映射（loadAll 时从 collections.json 建映射）。代价：两处数据要同步（集合改名时内存 id 不变、文件名字要更新），F1-F3 阶段集合操作少，可接受；面试可展开"对外契约用语义化标识、内部实现用结构化标识"的设计思想。

### Q8：重命名笔记为什么只改 frontmatter title，不改文件名？
**答**：文件名和 title 职责不同（F1 决策）：文件名是**存储标识**（新建时定死，防自动保存把标题当文件名导致"搬家"和互相覆盖），title 是**显示名**（侧边栏、Obsidian、引用系统都用它）。改文件名的连锁代价：① 同名冲突检测（文件名唯一性）；② idToPath 映射重建；③ 后端向量索引按文件路径关联（B6 按文件建索引），改名 = 旧索引残留 + 新索引未建。MVP 只改 title 已满足"笔记名可改"；Obsidian 式"改名=改文件"留到需要时（或 Tauri 版）再做。面试加分：这是"显示层与存储层解耦"的又一实例，和文献 `{id}_{原名}.pdf` 命名（B5）同一思想。

## ④ 踩坑经历

### Q1：复制来的 .venv 是空壳，怎么发现和修复的？
**背景**：项目的 .venv 是从 fastapi-note-server 复制来的，只复制了 python.exe/pythonw.exe，没有 pip、Scripts、site-packages。
**发现**：`pip install -r requirements.txt` 报 `No module named pip`。
**修复过程**：先 `python -m venv .venv` 修复，结果 `--version` 显示 Python 3.8.2——PATH 里的 `python` 是 D:\PYTHON 下的 3.8，而原 venv 基于 3.12。3.8 太老（langchain 0.3+ / python-docx 1.1+ 要求 ≥3.9），于是用原 base 解释器（`C:\Users\ji'jie\AppData\Local\Programs\Python\Python312\python.exe`）`-m venv --clear .venv` 重建。
**教训**：Windows 多 Python 环境，venv 相关操作前先 `python --version` + 看 `pyvenv.cfg`，确认解释器版本与预期一致；`python -m venv` 对已存在目录是"补齐"模式，`--clear` 才清空重建。

### Q2：arXiv API 请求返回 301，为什么？怎么修？
**背景**：`http://export.arxiv.org/api/query` 现在返回 301 重定向到 https，而 **httpx 默认 `follow_redirects=False`**（requests 默认 True），所以 `raise_for_status()` 直接抛 HTTPStatusError，被兜底捕获返回 `{}`——表现为"查不到"。
**修复**：API 地址换 https 直连 + 客户端显式 `follow_redirects=True`。
**教训**：httpx 与 requests 的默认行为差异是知名陷阱，用 httpx 时 HTTP 异常要区分"网络失败"和"3xx 重定向未跟随"；元数据兜底返回 `{}` 的设计让这类问题表现为"静默失败"，排查时要先看原始响应而不是只看返回结果。

### Q3：为什么 10.48550/arXiv.xxx 这个 DOI 在 Crossref 查不到？
**背景**：arXiv 论文的 DOI（10.48550/...）由 **DataCite** 注册，不是 Crossref。用 Crossref API 查它返回 404。
**教训**：DOI 前缀按注册机构分区（10.1109→IEEE/Crossref、10.48550→DataCite、10.1007→Springer...）。本项目只接 Crossref，DataCite 前缀的 DOI 走兜底手动录入即可——这是"知道自己没做什么"的边界意识，面试时主动说明可加分。

### Q4：验证 uvicorn 时 taskkill 误伤风险
**背景**：用 `taskkill //F //IM python.exe` 结束验证用的 uvicorn，会把机器上所有 python 进程都杀掉。
**教训**：多进程环境不要用镜像名杀进程，应该按端口找 PID（如 `netstat -ano | findstr 3001`）精准清理。本地开发机有多个服务并行时尤其注意。

### Q5：F1 文件命名方案被调用方行为推翻
**背景**：设计 F1 时最初想"文件名 = 笔记标题"（直观、可读）。写代码前通读 editor/index.tsx 的 `debouncedSaveCurrentNote`，发现自动保存会把 title 改成正文第一行 30 字符——title 根本不是稳定值，若文件名跟着走，每次改首行笔记文件就"搬家"，同标题还会互相覆盖。
**修复**：文件名在新建时确定（当时标题 + 重名序号），此后不变；title 变化只改内存。
**教训**：改造存储层前，先读调用方的**实际调用语义**而不是只看接口签名；"对外签名不变"只保证编译不报错，不保证行为符合预期。面试主动讲这个，展示"先读代码再动手"的工程习惯。

### Q6：PRD 假设的 extendMarkdown 在 tiptap-markdown@0.9 里不存在
**背景**：PRD 9.4 写"引用标记的 markdown 序列化用 tiptap-markdown 的 extendMarkdown 扩展"。开工前探测 dist 源码：`extendMarkdown` 出现 0 次、无 nodes/marks 自定义入口——0.9.0 根本不支持自定义节点序列化。
**处理**：F2 采用"0.9.0 现有能力 + 背景色降级"（PRD 9.6 风险表已留退路）；extendMarkdown 需求推迟为 F6 前置调研（升级版本或自写 serializer）。
**教训**：依赖能力以**实际探测**为准（grep dist 源码、跑最小用例），不轻信文档/PRD 假设；方案设计要预留降级路径。这也是"技术调研先行"的面试加分点。

### Q7：gray-matter 在浏览器报 `Buffer is not defined`，怎么定位和修复的？
**背景**：用户反馈保存笔记只有 frontmatter 没有正文（空内容能存、非空内容崩）。拿到报错栈后定位：gray-matter 的 `lib/utils.js toBuffer` 直接用全局 `Buffer.from(input)`（浏览器没有全局 Buffer）；而 `matter('')` 对空串短路返回，不触发 toBuffer——所以新建（空内容）成功、自动保存（非空）崩溃。js-yaml 的 buffer 引用则被 Vite/esbuild 预构建安全 stub 了（try/catch 包裹，binary 类型自动降级），所以浏览器可用。
**修复**：弃用 gray-matter，自研 `src/lib/frontmatter.ts`（js-yaml@4 直接 parse/stringify，~50 行），复刻 gray-matter 输出格式保证兼容；bundle 反而减小 275KB（gray-matter 的外壳依赖 section-matter/kind-of/strip-bom-string 全省）。
**教训**：① Node 环境有全局 Buffer，**Node 测试通过 ≠ 浏览器可用**，涉及 Node 全局（Buffer/process）的依赖必须做浏览器侧验证（vite prebundle + 实际调用）；② 依赖的"输入形态分支"要全覆盖——短路路径（空值）正常不代表主路径正常；③ 排查从**用户报错栈**入手，不要自己猜。

### Q8：F3 设计 review 发现"重命名会被自动保存覆盖"的冲突
**背景**：设计侧边栏重命名时，先读 editor 的自动保存代码（`debouncedSaveCurrentNote`），发现它每次保存都用正文第一行覆盖 title——若直接加重命名按钮，用户改名后下次编辑正文就被第一行覆盖，重命名形同虚设。
**处理**：title 权威化——自动保存不再计算/覆盖 title，title 只由新建与重命名决定（用户确认接受"标题不再自动跟随第一行"的行为变化）。
**教训**：加新功能前**先读相关调用方的现有行为**（和 F1 的"文件名方案被 title 动态性推翻"是同一类坑的第二次命中）——"接口/行为现状"是设计的硬约束，不是可以忽略的细节。面试主动讲"我读代码发现 X 冲突，所以改为 Y"，展示设计前的代码审查习惯。

## ⑤ 原理深挖

### Q1：OpenAI 兼容协议是怎么回事？为什么 DeepSeek 和 SiliconFlow 都能复用 openai SDK？
**答**：OpenAI 在行业里的地位让它的事实 API 规范成了标准接口：`/v1/chat/completions`（聊天）、`/v1/embeddings`（向量）、以及 2024 年底引入的 `/v1/responses`。DeepSeek、SiliconFlow、Moonshot 等国内厂商都实现了与 OpenAI 相同的请求/响应 JSON 结构，只需要在 SDK 里改 `base_url` 和 `api_key`。好处是：客户端零适配，一套 SDK 接所有兼容服务商，切换厂商只改配置。这也解释了为什么本项目 architecture 能保持"LLM 和 embedding 共用一个 openai SDK"。

### Q2：目录穿越攻击怎么防？为什么不能用字符串前缀比较？
**答**：核心是两步——`target = (vault / relative).resolve()` 先解析出真实路径（折叠 `..`、跟随符号链接），再用 `target.is_relative_to(vault)` 判断是否还在 vault 内。为什么不能 `target.startswith(vault)`？① 路径语义问题：`/vault/../etc/passwd` 字符串前缀不匹配 `/vault/`，但实际指向 vault 之外；`..` 折叠是路径语义操作，不是字符串操作。② 符号链接：vault 内一个软链指向外部目录，字符串比较看不出，`resolve()` 会展开成真实路径。③ Windows 大小写与分隔符差异。面试补充：`is_relative_to` 是 Python 3.9+ 的 `pathlib` 标准方法，避免手写 commonpath 比较。

### Q3：导入 PDF 时文件名为什么用 `{id}_{清洗原名}`？只存原名不行吗？
**答**：这是"系统标识 vs 用户标签"分离原则的应用（Zotero 的 storage/ABCD1234.pdf 同理）。纯原名的三个问题：① 重名覆盖——不同来源都叫 main.pdf 会互相覆盖，两个文献条目指向一个文件；② 文件名不可信——可能含 `../`（路径注入）、Windows 非法字符（保存报错）；③ 改名断链——用户改了文件名，应用的 pdfPath 就失效。方案 C（ID + 清洗原名）两全：ID 是 12 位 hex 保证唯一与内部关联（笔记引用、索引、删除都靠 ID 不靠文件名），清洗后原名（取 basename、非法字符替换、限长 100）保证 vault 对人类可读。面试加分：说"文件名属于展示层，ID 属于存储层，两层解耦"。

### Q4：导入流程里"双重降级"是什么？为什么这么设计？
**答**：导入 PDF 有两个"增强环节"——元数据补全和向量索引，两个都可能失败（网络、API key、embedding 服务挂了）。设计原则是**主流程（PDF 入库）绝不因增强环节失败而中断**：补全失败 → title 用文件名占位、照常入库；索引失败 → 跳过索引、照常入库。文献进了库就是成功，元数据可后续编辑（PRD 8.7 兜底），索引可由 B6 refresh 重建。面试加分：这是"核心路径 vs 增强路径"的职责分层，也是 PRD"embedding 失败降级"在导入侧的体现。

### Q5：为什么自动保存要"原子写"（tmp + os.replace）？直接写文件不行吗？
**答**：直接 `write_text` 在写入过程中崩溃（断电/进程被杀）会留下**半截文件**——前半是旧内容后半是新内容，Markdown 语法损坏甚至乱码。原子写：先写完整的 `.tmp` 文件，成功后 `os.replace(tmp, target)` 原子改名——操作系统保证要么旧文件完整、要么新文件完整，不存在中间态。本项目笔记自动保存是 600ms 防抖、高频写，每次写都值得保护。面试补充：`os.replace` 在 Windows 和 POSIX 同卷都是原子的（`os.rename` 在 Windows 上已存在目标时会失败，replace 可覆盖）。

### Q4：增量索引为什么用 mtime+size 比对，不用文件内容 hash？
**答**：hash（如 MD5）要对每个文件**全读一遍**计算，千级文件时 CPU 和 I/O 开销大；mtime+size 是文件系统元数据，stat() O(1) 获取，遍历一千个文件只做一千次 stat。代价是精度：手动改 mtime 或 size 相同内容不同（极小概率）会漏检。个人本地场景，成本换精度值得。面试补充：生产级系统可用"mtime 快速比对 + 变更文件 hash 二次确认"的两级策略。

### Q5：启动时自动扫描为什么用 FastAPI lifespan？失败为什么不阻断启动？
**答**：lifespan 是 FastAPI 官方推荐的启动/关闭钩子（旧版 @app.on_event("startup") 已弃用），@asynccontextmanager 包裹，yield 前是启动逻辑。扫描索引是**辅助任务**：vault 可能还没建（首次启动）、API key 可能没配——这些都不该挡住服务起来。所以 try/except 捕获后打印警告继续启动，前端拿到 404 也能正常提示。面试补充：启动任务的取舍——阻断式（强一致）vs 非阻断式（可用性优先），本项目选后者。

### Q6：RAG 检索结果为什么注入 system prompt 而不是拼在 user 消息里？
**答**：两个原因。① 语义分层：system 消息定义助手的角色与回答约束，检索结果是"回答时该参考的资料"，属于系统层约束——就像给员工发任务时附上参考资料，而不是让客户把资料说一遍。② 安全：user 消息内容可能包含恶意指令（prompt 注入），如果检索上下文拼进 user 消息，攻击者可以伪造检索文本诱导模型；system 层由服务端拼接，用户无法触碰。实现上：system content = 模板.format(note_context) + rag_text 字符串拼接，SSE 协议逐字节不变。

### Q7：RAG 检索失败为什么"静默降级"？用户不知道检索失败不奇怪吗？
**答**：这是"增强能力 vs 主流程"的职责分层。RAG 是问答的增强项：检索失败（embedding 服务挂、key 失效、网络断）不等于问答失败——模型依然可以凭自身知识回答。静默降级 = 失败时走无 RAG 的普通对话，SSE 协议不变、前端打字机无感知。为什么不提示用户"检索失败"？① 提示会让用户困惑（"我没问检索的事"）；② 失败可能是瞬时的，下次请求就恢复；③ 若回答质量问题用户可感知，再排查。真正的错误（chat API 挂了）才需要报错——那是主流程失败。面试补充：这是 B5 双重降级、B6 启动扫描非阻断一脉相承的设计哲学。

### Q8：检索质量差是什么原因？怎么排查的？
**答**：真实案例：全局检索"RAG 管线的四个环节"时，198 块的英文大文献把真正相关的中文笔记块（1 块）压到第 72 名。排查链路：① 先排除代码——集合向量唯一性检查（199/199 唯一）、向量归一化检查（范数 1.0）、存储向量与实时重嵌一致性（cosine=1.0000）、embed_query 与 embed_documents 一致性（cosine=1.0）——全部正常；② 再看内容——最高相似度块是 PDF 的**页眉/页脚噪音**（每页重复的期刊名+卷期页码"Journal of Environmental Management 410 (2026) 130053"），这些短文本块嵌入判别力弱、与 query 相似度虚高（0.69）。结论：不是代码 bug，是**内容噪音**问题。改进方向：抽取时按规则过滤页眉页脚、或检索时过滤过短块。面试加分：把"先排除代码、再看数据"的排查方法论讲出来，比直接说结论更打动面试官。

### Q9：langchain 只有同步 API，async 路由里怎么用？（阻塞与调度）
**答**：kb.py 全部同步实现（OpenAIEmbeddings/Chroma 只提供同步方法），async 路由（B5/B7）里用 `anyio.to_thread.run_sync(kb.upsert_document, ...)` 包一层。原理：`to_thread` 把函数丢进线程池执行，主线程 await 结果，事件循环不被阻塞。为什么核心不写 async？① 同步核心测试/CLI 简单（B3 的 CLI 验证就是直接调用）；② 调度方式应由调用侧决定（将来若是批处理任务，根本不需要 async）；③ 避免"假 async"——内部还是同步 API，包装成 async 反而误导。面试考点：async 环境里调用同步阻塞函数是常见事故（"blocking the event loop"），to_thread 是标准解法。

### Q3：embedding 和 chat 模型为什么必须分开？（架构理解题）
**答**：这是两个不同能力的模型。chat 模型（如 deepseek-chat）是生成式大模型，输入文本输出文本，训练目标是对话/生成质量；embedding 模型（如 bge-m3）是表征模型，输入文本输出固定维度向量，训练目标是语义相似度。RAG 流程中 embedding 负责"把文档和问题都变成向量做相似度检索"，chat 负责"根据检索结果生成回答"。DeepSeek 官方只提供 chat 不提供 embedding，所以需要 SiliconFlow 补位。

### Q3：分块参数为什么是 chunk_size=500 / overlap=50？中文分隔符起什么作用？
**答**：500 是经验值——块太小语义不完整，块太大超出 LLM 上下文窗口且检索粒度变粗（无关内容混入）。50 的 overlap 保证块边界处的语义不断裂（前后文承接）。分隔符列表加了 `。！？；，` 等中文标点：英文默认分隔符只有 `\n\n \n 空格`，对中文文本会在句子中间硬切，块边界落在逗号上甚至词中间；加上中文标点后，RecursiveCharacterTextSplitter 优先按句号切块，边界语义完整。这也是 langchain 官方 splitter 的"优先级尝试"机制——按分隔符顺序逐个尝试切分。

### Q4：Chroma 持久化为什么放在 vault/.kb 下？为什么不入库？
**答**：vault 是数据真源（PRD 5.2 决策），`.kb` 是应用内部元数据，由后端维护。向量库可由后端重建（重新扫描 + embedding），是**派生物而非原始数据**——所以 .kb 不入 git、损坏可删。这是"原始数据 vs 派生数据"分层：笔记 .md 和 PDF 是原始数据（用户资产，进云盘/Git），chroma_db 是派生索引（只存向量和 chunk 文本，删了重新生成）。面试加分点：派生数据不进备份体系，坏了重建即可，这是数据可靠性设计。

### Q5：Crossref 的 "polite pool" 是什么？
**答**：Crossref 约定：请求 `api.crossref.org` 时带上 `mailto=你的邮箱` 参数，标识身份后，请求被划入"礼貌池"，限流阈值比匿名请求宽松得多，且能拿到专属的技术支持。这是公开 API 的**公平使用**惯例：让服务方知道谁在调用、便于联系。本项目请求频率低，加它是行业规范意识；面试答"公开 API 的尊重性设计 + 我们频率低无所谓"即可。类似的还有 arXiv 的 rate limit（每 3 秒一次）提醒。

### Q6：StorageAdapter 为什么每个方法都返回 Promise？接口设计要考虑什么？
**答**：文件系统在浏览器和桌面环境都是**异步 API**（fetch、Tauri fs 插件都是 Promise），接口如果设计成同步，实现层只能靠阻塞模拟（浏览器里做不到），发布期 Tauri 实现就接不上了。接口从第一天就异步，是所有实现方（HTTP/Tauri/mock）的"最小公倍数"约束。第二个原则是 **YAGNI（You Aren't Gonna Need It）**：接口只有 6 个方法，没有 `readBinary`（读 PDF 二进制，对应 `GET /api/fs/file`）——F5 才需要，到时候在接口上加一个方法即可，接口演进是允许的，但不要提前加用不到的方法。面试加分：接口设计 = "为所有实现方的最小公倍数设计 + 只给当前需求建模"，过度设计（提前加一堆方法）和设计不足（绑死某种实现）都是坑。

### Q7：笔记保存为什么"全量重写"整个文件？不增量 patch 吗？
**答**：每次保存用 gray-matter.stringify 把 frontmatter + 正文整体重新生成、整文件写入。为什么不增量 patch？① 简单可靠——frontmatter 字段少（4 个），全量生成是纯函数、无状态，不存在"哪个字段没同步"的中间态；② 后端 write 是原子写（tmp + os.replace），全量重写不会产生半截文件；③ 文件小（笔记 KB 级），性能无感。代价：外部工具（Obsidian）同时改了文件时，全量重写会覆盖外部修改——这是 F3 轮询/冲突检测要解决的问题。面试可对比"增量 patch"（需解析定位 + 状态机，复杂且易错）与"全量重写"（简单，适合小文件）的适用场景。

### Q8：文献导入的"降级"在前后端是怎么配合的？（B5 双重降级的前端视角）
**答**：后端 B5 的降级设计（元数据补全失败 → title 占位；索引失败 → 跳过）保证了"PDF 入库是主流程"，前端不需要感知失败细节：POST 总是 201 返回一个完整 entry（title 可能是文件名占位、authors 可能为空）。前端的配合是：①导入面板展示补全结果（含"作者未知"等空态），用户肉眼确认是否手动补元数据；②错误只在**真正阻断**时出现（非 PDF 400、重复导入 409、超 50MB）——这些是前端也可以预先校验的（后缀校验前端已做，重复依赖后端）。面试加分："降级设计"的本质是**把增强功能与主流程解耦**（PRD 8.7 元数据可后续编辑的兜底），前端 UI 要区分"展示空态"（正常降级）与"报错"（真正失败）。
