# documents.py 流式写盘通俗讲解：水管 vs 水桶

> 用大白话讲清楚 `backend/app/routers/documents.py` 里"导入 PDF 时把文件从请求写到磁盘"的这段代码，以及它背后的设计道理。

## 一、先看代码（documents.py 导入流程第 2 步）

```python
lit_id = uuid.uuid4().hex[:12]                        # 生成文献 ID
saved_name = f"{lit_id}_{_clean_filename(filename)}"  # 拼新文件名（方案 C）
pdf_rel = f"文献/{saved_name}"                        # vault 相对路径
pdf_abs = default_vault_path() / pdf_rel              # 磁盘绝对路径
pdf_abs.parent.mkdir(parents=True, exist_ok=True)     # 确保 文献/ 目录存在

size = 0
try:
    with pdf_abs.open("wb") as out:                   # 打开文件准备写
        while True:
            chunk = await file.read(1024 * 1024)      # ① 每次只读 1MB
            if not chunk:                             # ② 读完了？
                break
            size += len(chunk)                        # ③ 累计已写字节数
            if size > MAX_FILE_SIZE:                  # ④ 超 50MB 了？
                raise HTTPException(400, "文件超过 50MB")
            out.write(chunk)                          # ⑤ 把这 1MB 写进磁盘
except HTTPException:
    pdf_abs.unlink(missing_ok=True)                   # ⑥ 超限：删掉写了一半的文件
    raise                                             # ⑦ 把 400 继续抛给前端
finally:
    await file.close()                                # ⑧ 无论成败，释放上传句柄
```

## 二、这段代码在干嘛：一句话

> **把浏览器传来的 PDF，一小块一小块地搬进磁盘，搬的过程中随时查"超没超 50MB"，超了就把搬了一半的丢掉。**

## 三、为什么是"水管"而不是"水桶"（核心问题）

**原始直觉做法**：`contents = await file.read()` 把整个文件读进内存，再一次性 `out.write(contents)`。就像拿水桶——先把一池子水全舀进桶里，再提去倒。

**这段代码的做法**：循环 `read(1MB)` → `write(1MB)`，像接了一根水管——水从浏览器流进磁盘，**内存里永远只有 1MB 的存量**。

对比一下两种方式在"50MB 上限"下的内存占用：

| | 水桶（一次性 read） | 水管（循环 1MB） |
|---|---|---|
| 内存占用 | 最多 50MB（+解析缓冲） | 恒 1MB |
| 什么时候发现超限 | 读完之后 | 超限瞬间（写到第 51MB 前） |
| 用户等待 | 读完才动手写 | 边收边写，更快开始落盘 |

如果同时 5 个用户各传 50MB，水桶方案峰值内存 250MB+，水管方案始终几 MB。**个人项目单用户可能无感，但这是服务端处理的通用素养**——面试被问"大文件上传你怎么处理"，答"流式边读边写、固定缓冲、边写边校验"就是标准答案。

## 四、逐段拆解：为什么每一步都这么写

### ① `await file.read(1024 * 1024)` —— 为什么是 await？为什么是 1MB？

`file` 是 FastAPI 的 `UploadFile`，它的数据**还在网络请求里，不在内存**。`read()` 是异步的：去网络的"水管"里取水，取到才返回。`1024 * 1024` 是每次取水的量——1MB。太小（比如 1KB）循环次数爆炸、太慢；太大（比如 10MB）内存缓冲变大。1MB 是常见折衷。

### ② `if not chunk: break` —— 怎么知道读完了？

网络流没有"总长度"，只有"取到空 = 流结束"。这是水管逻辑的核心：**不知道总共多少水，只能一直接，直到接不到**。

### ③ `size += len(chunk)` —— 为什么要自己数？

为什么不直接问"这个文件多大"？两个原因：
- 请求头里的 `Content-Length` **不可信**（可以被伪造，multipart 场景还不一定有）
- 数"实际写进去多少"才是真相——size 就是"已经落盘了多少字节"

### ④ `if size > MAX_FILE_SIZE: raise` —— 为什么边写边查？

超限检查**必须在写的过程中**做，而不是写完了再检查——写完 100MB 再删，内存和磁盘都白折腾。水管方案天然支持"边放水边看水表，超了马上关闸"。

### ⑤ `out.write(chunk)` —— 写文件为什么不用 await？

这是**磁盘**，不是网络。`with pdf_abs.open("wb")` 打开的是普通文件，同步写。异步只针对网络 I/O（读上传流）；磁盘写是同步的。这里没混——`await file.read()` 管网络，`out.write()` 管磁盘。

### ⑥ `pdf_abs.unlink(missing_ok=True)` —— 超限后为什么删文件？

抛异常时文件已经写了一半（比如 40MB 的半截文件）。**留着就是垃圾**：占磁盘、下次导入还可能重复。`unlink` 删掉它。`missing_ok=True` 表示"删不到也不报错"——万一刚抛异常前文件没建成功（比如 0 字节都没写），删文件这步不能二次报错把真正的错误掩盖掉。

### ⑦ `raise` —— 为什么又抛一次？

`except HTTPException` 里删完文件，**把同一个异常原样抛回去**，FastAPI 会把它转成 HTTP 400 响应给前端。不吞掉错误——前端需要知道"超限了"这个事实。

### ⑧ `finally: await file.close()` —— 这个 finally 是干嘛的？

`try/except/finally` 的语义：**无论成功还是失败，finally 里的代码一定执行**。`file.close()` 释放 UploadFile 持有的临时文件句柄。不关会怎样？句柄泄漏——文件一直被占用，Windows 下后面想删都删不掉。这是"资源释放"的标准模式，面试问"finally 什么时候用"就是这个场景。

## 五、整个防御链串起来

```
打开文件 → 循环读网络流 → 超限？→ 抛错 → 删半截文件 → 再抛给前端
                       └→ 读完了 → 正常关闭
                       无论哪条路 → finally 关闭上传句柄
```

四层防御：**限大小（边写边查）** → **失败清理（删半截）** → **错误上抛（前端知情）** → **资源必释放（finally）**。任何一层缺失，都可能留下脏文件或泄漏句柄。

## 六、面试问答预演

> **"大文件上传你怎么处理？"**
>
> 答：FastAPI 的 `UploadFile` 配合流式读写——循环 `await file.read(1MB)` 边读边写磁盘，内存恒定 1MB；循环内累计实际写入字节数做 50MB 上限校验（不信 Content-Length，信自己数的）；超限抛 400 并删除已写半截文件；finally 里关闭上传句柄防止资源泄漏。核心思想是：网络流按块消费、边消费边校验、失败要清理现场、资源必须释放。

> **"为什么不直接 file.read() 读完再写？"**
>
> 答：一次性 read 会把整个文件加载进内存（50MB 上限下峰值 50MB），且要等全部收完才开始写；流式方案内存恒 1MB、边收边写、超限即刻发现。对大文件服务这是并发场景下的内存安全底线。
