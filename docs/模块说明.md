# 模块说明：B1 后端基建（依赖 + 配置）

> 交付时间：2026-08-12 ｜ 分支：backend ｜ WBS：B1（0.5d）

## 解决的问题

B2（元数据补全）、B3（RAG 知识库）、B5（文献导入）、B8（导出）都要使用 embedding、向量库、PDF 抽取、文件上传、docx 生成能力。B1 一次性铺好依赖与配置位，后续模块直接复用，不重复安装/不各自写配置读取。

## 数据流（配置流）

```
.env ──load_dotenv──► config.py(Settings dataclass) ──► 各模块 import settings
  DEEPSEEK_API_KEY ─────────────► settings.deepseek_api_key ──► main.py /api/chat（现有）
  SILICONFLOW_API_KEY ──────────► settings.siliconflow_api_key ──► B3 embedding
  SILICONFLOW_BASE_URL ─────────► settings.siliconflow_base_url ──► B3 OpenAIEmbeddings
  EMBEDDING_MODEL ──────────────► settings.embedding_model ──► B3（默认 BAAI/bge-m3）
  VAULT_PATH / KB_DIR ──────────► settings.vault_path / kb_dir ──► B3/B4（默认推导待定）
  PORT ─────────────────────────► settings.port ──► uvicorn
```

## 接口清单（Settings 字段）

| 字段 | 默认值 | 用途 |
|---|---|---|

| vault_path | "" | vault 根目录（未配置，B3 定默认） |
| kb_dir | "" | .kb 元数据目录（未配置） |

## 关键决策

1. **LangChain 拆包，不装大包**：langchain 0.3+ 官方架构，核心在 langchain-core，集成独立成包。只装检索侧需要的 4 个包（core/openai/text-splitters/chroma），避免拖入几十个无用集成。`langchain-deepseek` / `langchain-community` 不需要——LLM 层不进 LangChain。
2. **LLM 不走 LangChain**：DeepSeek 是 OpenAI 兼容协议，现有 main.py 用 openai SDK 直连（`AsyncOpenAI(base_url=deepseek)`）。B7 做 RAG 注入只是往 system prompt 拼检索结果，SSE 协议逐字节不变（PRD 9.2 硬性要求）。LangChain 只承担 embedding/分块/向量库（检索侧）。
3. **保持 dataclass + dotenv**：与现有 3 字段一致、frozen 不可变、零新依赖。未引入 pydantic-settings（后续配置变复杂再迁移）。
4. **版本约束 `>=x,<y`**：语义化区间而非 pin 死，pip 自动解析兼容版本，兼顾稳定与可升级。
5. **VAULT_PATH/KB_DIR 只铺位不拍板**：vault 是用户自选文件夹，默认推导逻辑与前端首次启动引导联动，交给 B3/B4 决策，避免过度设计。

## 验证结果

- 8 个新依赖安装成功（pip 清华镜像），无版本冲突
- langchain_openai / langchain_text_splitters / langchain_chroma / langchain_core、pypdf / python-docx / bs4 / multipart 全部可导入
- `/health`、`/`、`/api/chat`（SSE 错误分支）验证通过，现有代码零影响

# 模块说明：B2 元数据补全服务（backend/app/metadata.py）

> 交付时间：2026-08-12 ｜ 分支：backend ｜ WBS：B2（1d）

## 解决的问题

文献导入时自动补全元数据：输入 DOI 或 arXiv ID → 调免费公开 API → 返回规范化字段。B5 的 `POST /api/documents` 会调用本模块，失败时走手动录入。

## 数据流

```
identifier（"10.xxxx/xxx" 或 "2401.xxxxx"）
   │ detect_id_type()（正则：DOI / arXiv 新老版 / none）
   ├─ doi ─► GET api.crossref.org/works/{doi} ─► JSON message ─► normalize_crossref()
   └─ arxiv ─► GET export.arxiv.org/api/query?id_list={id} ─► Atom XML ─► normalize_arxiv()
                                   │
                        统一返回规范 dict，失败一律 {}
```

## 接口清单

| 函数 | 签名 | 说明 |
|---|---|---|
| `detect_id_type` | `(str) -> Literal["doi","arxiv","none"]` | 正则识别标识符类型 |
| `fetch_metadata` | `async (str) -> dict` | 统一入口（B5 只调这个） |
| `fetch_by_doi` | `async (str) -> dict` | Crossref GET + 规范化 |
| `fetch_by_arxiv` | `async (str) -> dict` | arXiv Atom XML + 规范化 |
| `normalize_crossref` / `normalize_arxiv` | `(Any) -> dict` | 纯函数：API 原始响应 → 规范 dict |
| `_parse_authors_crossref` / `_parse_author_name` / `_parse_year` | 辅助 | 作者/年份解析 |

**输出字段**（对齐 PRD 5.4 literature.json）：`title, authors[{given,family}], year, venue, volume, issue, pages, doi, arxivId, keywords`

## 关键决策

1. **httpx 异步客户端，不用 requests**：FastAPI 全链路 async，httpx 不阻塞事件循环；requests 同步会卡住并发。已显式声明进 requirements（直接依赖显式化）。
2. **作者存结构化 `[{given, family}]`**：为 B8 导出格式化铺路（GB/T 7714 要"姓 名缩写"、APA 要"Smith, J."，前提是姓名有边界）。arXiv 名字字符串按"最后 token 为 family"解析；Crossref 直接有 given/family；机构作者名放入 family。
3. **bs4 解析 arXiv Atom XML**：命名空间前缀（arxiv:journal_ref）用"tag name endswith 前缀"匹配，兼容两种写法。
4. **失败兜底统一返回 `{}`**：网络错误/404/超时/解析失败一律空 dict，调用方 `if not metadata:` 走手动录入。增强功能失败不打断主流程。
5. **Crossref 带 `mailto` 参数**（polite pool）：限流更宽松的行业惯例。
6. **CLI 入口**（`python -m app.metadata <id>`）：演示/调试/面试 demo 用。

## 验证结果

- 纯函数断言：类型识别（doi/arxiv/老版/乱输）、作者解析、Crossref 规范化全过
- 真实 arXiv `1706.03762` → Attention Is All You Need（year=2017，keywords=[cs.CL]）
- 真实 DOI `10.1109/CVPR.2016.90` → Deep Residual Learning（year=2016，venue=CVPR 全称，pages=770-778）
- 兜底：不存在的 DOI → `{}`；非识别格式 → `{}`

## 踩坑记录

- **arXiv API 301 重定向**：`http://export.arxiv.org` 现在跳转 https，而 **httpx 默认不跟随重定向**（`follow_redirects=False`，与 requests 的默认 True 相反）→ 换 https URL + 显式 `follow_redirects=True`。
- **10.48550 前缀不在 Crossref**：arXiv 的 DOI（10.48550/...）由 **DataCite** 注册，Crossref 查会 404。这是预期行为，兜底处理即可。

# 模块说明：B3 知识库核心（backend/app/kb.py）

> 交付时间：2026-08-13 ｜ 分支：backend ｜ WBS：B3（1.5d）

## 解决的问题

RAG 的地基：把笔记/PDF 文本变成可检索的向量索引，提供**写入（幂等 upsert）、删除、检索（支持单篇限定）**。B6 扫描 vault 时调 upsert，B7 问答时调 retrieve。

## 数据流

```
笔记纯文本 / PDF 文件
   │  extract_pdf_pages()（pypdf 逐页抽取，保留页边界）
   ▼
split_pages()：RecursiveCharacterTextSplitter(500/50，分隔符含中文标点)，页内分块
   │  每块带 metadata：page / docType(note|paper) / docId / title
   ▼
upsert_document()：先 delete(where=docId) → OpenAIEmbeddings(SiliconFlow, bge-m3) → Chroma.add
   ▼
backend/vault/.kb/chroma_db/（持久化，可删可重建，见 ADR-0001）
   │
retrieve(query, doc_id=None, top_k=5)：similarity_search(filter)
   ├─ 全局：filter=None
   └─ 单篇：filter={"docId": doc_id}
   ▼
返回 LangChain Document 列表（page_content + metadata）→ B7 注入
```

## 接口清单

| 函数 | 签名 | 说明 |
|---|---|---|
| `extract_pdf_pages` | `(str\|Path) -> list[str]` | pypdf 逐页抽取 |
| `split_pages` | `(list[str]) -> list[Document]` | 页内分块，空块过滤 |
| `upsert_document` | `(doc_type, doc_id, title, pages=None, text=None) -> int` | 幂等写入，返回块数；doc_type ∈ note/paper |
| `delete_document` | `(doc_id) -> None` | Chroma delete where docId |
| `retrieve` | `(query, doc_id=None, top_k=5) -> list[Document]` | 相似度检索 |
| `get_collection` | `() -> Chroma` | 懒加载单例 |
| `_default_vault_path` / `_kb_root` / `_chroma_dir` | 路径推导 | 见 ADR-0001 |

## 关键决策

1. **vault 默认路径（ADR-0001）**：`VAULT_PATH` 未配置 → `backend/vault`（开发期）；`.env` 优先；发布期由前端交互引导用户指定后写入。`KB_DIR` 未配置 → `{vault}/.kb`，Chroma 存 `{vault}/.kb/chroma_db`。
2. **同步核心 + 调用方 to_thread**：langchain embedding/Chroma 仅同步 API，kb.py 保持纯同步；async 路由（B5/B7）用 `anyio.to_thread` 包一层，不阻塞事件循环。
3. **页级分块**：块不跨页，metadata.page 准确——RAG 回答要附来源页码（PRD 5.6）。代价：页末块可能不足 500 字。
4. **幂等 upsert**：先删旧块再 add，B6 重复索引结果一致。
5. **单例懒加载**：首次调用 `get_collection()` 才建立 Chroma 连接；**初始化校验 SILICONFLOW_API_KEY**，缺失即抛错（明确失败），B7 的降级逻辑在调用侧。
6. **中文标点分隔符**：`["\n\n","\n","。","！","？","；","，"," ",""]`，块边界落在句号处。
7. **元数据约定**（PRD 5.4）：`docType / docId / page / title`，全部 Chroma 基础类型。

## 验证结果（真实 embedding，SiliconFlow API）

- 纯函数：分块页码/空块过滤/中文标点边界；空白 PDF 抽取 2 页不崩
- 全链路：upsert 2 篇中文文档 → 语义查询命中正确文档 → 单篇限定（where 过滤）生效 → delete 后检索不到
- `.kb` 结构确认：`vault/.kb/chroma_db/chroma.sqlite3`（chromadb 1.x 直接存 sqlite3，无嵌套 .chroma）

## 范围边界

- **retrieve 是查询能力**（返回 Document 列表即止）；**B7 的检索注入**（检索结果 → system prompt、降级、来源标注）由用户亲手实现。

# 模块说明：B4 vault 文件 API（backend/app/routers/fs.py + app/vault.py）

> 交付时间：2026-08-14 ｜ 分支：backend ｜ WBS：B4（1d）

## 解决的问题

开发期浏览器无法直接读写本地文件（File System Access API 仅 Chromium 且要授权），后端提供 vault 内文件读写的 HTTP 兜底；F1 的 `HttpFsAdapter` 调它，发布期换 Tauri 原生 fs 插件，业务代码零改动（PRD 8.3）。

## 接口清单（`/api/fs/*`，path 为 vault 内相对路径）

| 方法 | 路径 | body | 说明 |
|---|---|---|---|
| GET | `/api/fs/list?path=` | — | 列目录 → `{entries: [{name, isDir, path}]}`，目录优先排序 |
| GET | `/api/fs/read?path=` | — | 读文本（utf-8）→ `{content}` |
| GET | `/api/fs/file?path=` | — | 二进制流（PDF），FileResponse |
| POST | `/api/fs/write?path=` | `{content: str}` | 创建/覆盖一体，原子写 |
| POST | `/api/fs/mkdir?path=` | — | 建目录（多级） |
| DELETE | `/api/fs/delete?path=` | — | 删文件/空目录（非空拒绝） |
| GET | `/api/fs/exists?path=` | — | → `{exists}` |

错误约定：越界 403 / 不存在 404 / 类型不匹配或失败 400 / 写入失败 500，body 为 `{"detail": ...}`。

## 关键决策

1. **防目录穿越（核心安全）**：`(vault / relative).resolve()` 后必须 `is_relative_to(vault)`。`resolve()` 折叠 `..` 与符号链接得真实路径，`is_relative_to` 做包含判断——不能用 `str.startswith`（`/vault/../etc` 字符串前缀不匹配但语义越界）。
2. **原子写**：先写 `name.tmp` 再 `os.replace`。自动保存 600ms 防抖高频写，直接写文中途崩溃留半截文件；os.replace 同卷原子（旧/新文件二选一完整）。
3. **路由模块化**：B4 起建 `app/routers/` 包，main.py `include_router(prefix="/api/fs")`。B5-B8 陆续挂载各自 router，main.py 不再膨胀。
4. **路径推导下沉 `app/vault.py`**：kb.py 的路径函数挪为 `default_vault_path()/kb_root()/chroma_dir()` 公共函数，kb/fs/B5 共用一处定义。
5. **read（文本 JSON）与 file（二进制流）分离**：PDF 不走 base64 包装（膨胀 33% + 前端解码）。
6. **delete 只删空目录**：rmdir 保守策略，防误删整棵目录树；递归删除由调用方按需实现（MVP 无此场景）。
7. **write 用 POST 而非 PUT**：创建/覆盖一体、path 在 query，无资源定位语义，POST 更简单。

## 验证结果

- 全流程：list 根 → mkdir → write（含中文路径/换行）→ read 回读 → exists → list 子目录 → file 二进制下载（431 bytes）→ delete
- **穿越攻击专项**：`../config.py`、`..%2F..%2Fconfig.py`、`..%2F..%2F..%2FWindows%2Fwin.ini` → 全 403
- 错误分支：不存在 404、read 二进制 400、read 目录 400、非空目录删除 400、GET 打 delete 405、非法 body 422
- kb.py 回归：路径函数重构后 upsert→query→delete 正常

## 踩坑记录

- **Git Bash 里 curl 直接传中文字面量会损坏编码**（GBK 控制台），`--data-urlencode "path=文献"` 实际创建了乱码目录 → 验证改用 httpx（正确 UTF-8 编码）或 python quote 生成编码 URL。与后端无关，是测试工具链问题。

# 模块说明：F2 笔记 Markdown 化（frontend/src/lib/note-file.ts + useDataStore/editor 改造）

> 交付时间：2026-08-14 ｜ 分支：frontend ｜ WBS：F2（2d）

## 解决的问题

F1 把笔记存成"扩展名 .md、内容却是 Tiptap HTML"的过渡形态。F2 让笔记文件变成**真正的 Markdown + YAML frontmatter**（PRD 5.4），可被 Obsidian / VS Code 直接打开编辑，编辑器 round-trip 无损；同时把集合定义持久化到 `.kb/collections.json`（此前纯内存，刷新即丢）。

## 数据流

```
Editor（Tiptap + tiptap-markdown@0.9）
  保存：storage.markdown.getMarkdown()  ──►  serializeNote()（gray-matter.stringify 拼 frontmatter）
  读取：editor.commands.setContent(md)  ◄──  parseNoteFile()（gray-matter 拆 frontmatter）
        │                                        │
        ▼                                        ▼
   useDataStore（内存缓存）◄────────────────►  vault/笔记/xxx.md（HttpFsAdapter）
        │
        └─ .kb/collections.json（集合定义持久化）
```

## 接口清单

**`src/lib/note-file.ts`（新，纯函数，不依赖 store/adapter/编辑器）**

| 函数 | 签名 | 说明 |
|---|---|---|
| `serializeNote` | `(note, collectionName?) => string` | Note → frontmatter + Markdown 文本；无元数据时输出纯正文（避免空 `---` 包裹） |
| `parseNoteFile` | `(raw, fileName) => ParsedNoteFile` | 文件文本 → `{title, content, tags, cites, collectionName}`；无 frontmatter 时 title 回退文件名；tags/cites 容错单字符串 |

**frontmatter 字段**（对齐 PRD 5.4）：`title`（双源：frontmatter 优先，文件名兜底）、`collection`（存**集合名字符串**，Obsidian 兼容）、`tags`、`cites`。

**useDataStore 改动**：saveNote 内容换 markdown + serializeNote 写 frontmatter；loadAll 读 collections.json + parseNoteFile 解析；addCollection/deleteCollection 持久化 collections.json；moveNoteToCollection 立即重写笔记文件（更新 frontmatter collection）。

**editor 改动一行**：保存 `getHTML()` → `storage.markdown.getMarkdown()`。

**依赖**：新增 `gray-matter@4.0.3`。

**类型补充**：`src/types/tiptap-markdown.d.ts`——0.9 未对 Storage 做 module augmentation，手动声明 `editor.storage.markdown` 类型（已核验 dist 源码结构）。

## 关键决策

1. **extendMarkdown 不可用 → 降级策略**：探测确认 tiptap-markdown@0.9.0 **没有 extendMarkdown**（dist 源码 0 次出现、无 nodes/marks 自定义入口），与 PRD 9.4 假设不符。背景色等视觉 attribute 序列化时被丢弃（Markdown 无此语法，不崩只丢视觉，PRD 9.6 允许）；引用徽章 `[[cite:id]]` 是 F6 的事，届时升级版本或自写 serializer（F6 前置调研）。
2. **collection 存名字符串 + 内存数字 id**：frontmatter 人类可读、Obsidian 兼容；name↔id 映射在 useDataStore 内完成。
3. **全量重写**：每次保存 gray-matter.stringify 重写整个文件，不增量 patch；外部修改感知是 F3 轮询的事。
4. **title 双源**：`frontmatter.title` 优先、文件名为 fallback；编辑器自动保存仍写第一行（现状行为不变）。
5. **文件名新建时定死**（F1 决策延续）：title 变化只改 frontmatter 不搬文件。
6. **F1 遗留文件容错**：无 frontmatter 的 .md 正常解析（title 取文件名），不迁移不损坏。

## 验证结果

- 纯函数 round-trip 16/16（Node 24 type stripping 直接运行 note-file.ts）：frontmatter 全字段写读、无 frontmatter 容错、单字符串容错、YAML 特殊字符安全、无元数据纯正文
- useDataStore 端到端 20/20（rolldown 打包 store → Node 对真实后端）：collections.json 读写、frontmatter 写读、模拟刷新重载（笔记+集合恢复、name↔id 映射）、title 更新不搬文件、moveNoteToCollection 更新 frontmatter、deleteNote 删文件、同名冲突、**用户验证数据测试后自动恢复**
- `npx tsc -b` 通过；`npm run build`（tsc + vite）通过
- 踩坑确认：gray-matter 对含数字的字符串值（如 `1706.03762`）序列化为带引号 YAML（`- '1706.03762'`），解析无碍，但子串断言会误判（测试改用 gray-matter 解析后比较）

## 面试要点

见 `docs/面试问答.md` F2 条目（①Q6、②Q3、③Q7、④Q6、⑤Q7）。

## 踩坑记录

- **tiptap-markdown@0.9 无 extendMarkdown**：PRD 假设的功能在依赖里不存在。教训：**动手前验证依赖能力边界**（探测 dist 源码而非只看 README 声称），方案要留降级路径（PRD 9.6 的风险应对恰好覆盖）。

# 模块说明：B5 文献导入与管理 API（app/literature.py + app/routers/documents.py）

> 交付时间：2026-08-14 ｜ 分支：backend ｜ WBS：B5（1d）

## 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/documents` | multipart：`file` + 可选 `doi`/`arxivId`；201 返回 entry |
| GET | `/api/documents` | `{entries: [LiteratureEntry...]}`，importedAt 倒序 |
| DELETE | `/api/documents/{lit_id}` | 三连清理；404 不存在 |

`LiteratureEntry` 字段（对齐 PRD 5.4）：`id, title, authors[{given,family}], year, venue, volume, issue, pages, doi, arxivId, pdfPath(vault 相对), status, collectionIds, tags, importedAt`

## 关键决策

1. **数据层/路由层分离**：literature.py 只管 json 增删查（原子写 + 损坏重建），documents.py 编排 HTTP/文件/补全/索引。
2. **文件名 = `{lit_id}_{清洗原名}.pdf`（方案 C）**：ID 保证唯一与关联、清洗后原名保证 vault 可读性（用户决策，理由见 docs/kb 系列讲解的"系统标识 vs 用户标签"）。
3. **清洗规则**：取 basename、`\/:*?"<>|` 与控制字符替换为 `_`、限长 100 字符、空则 untitled——上传文件名不可信（路径注入/非法字符/超长）。
4. **重复检测**：DOI（大小写不敏感）/ arXiv ID 精确匹配 → 409（P0 要求）。
5. **双重降级**：元数据补全失败 → title 占位照常入库；索引失败（embedding/key/网络）→ 跳过索引。增强功能失败不阻断主流程（B2 的 `{}` 约定在此兑现）。
6. **流式写盘**：1MB 块边读边写，50MB 上限——不把整个文件读进内存。
7. **to_thread 调度**：extract_pdf_pages（CPU）+ upsert（embedding 网络 IO）同步函数经 `anyio.to_thread.run_sync` 调度（ADR-0002）。**注意 run_sync 只接受位置参数**（本次踩坑）。

## 验证结果（真实 arXiv PDF：1706.03762）

- 带 arxivId 导入：title/authors/year 全自动补全，201；文件名 `{id}_attention_is_all_you_need.pdf`
- kb 全局检索 3 条命中（page 2/4 论文原文）、单篇限定 2 条
- 重复导入 409；无标识符导入 title 占位（文件名 stem）；非 PDF 400；50MB 上限（代码路径）
- DELETE 三连：文件删、kb 检索 0 条、literature.json `[]`、无 .tmp 残留

## 踩坑记录

- **`anyio.to_thread.run_sync` 不接受关键字参数**：`run_sync(func, ..., pages=pages)` 抛 `TypeError: run_sync() got an unexpected keyword argument 'pages'` → 全部改位置参数（upsert_document 第 4 个位置参数即 pages）。
- **uvicorn 未加 `--reload` 导致修复不生效**：验证时改代码后服务仍跑旧代码，排查半天才确认是没重载——dev 启动命令必须带 `--reload`（CLAUDE.md 常用命令已如此约定）。
