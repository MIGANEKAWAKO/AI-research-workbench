# 模块说明：B1 后端基建（依赖 + 配置）

> 交付时间：2026-08-12 ｜ 分支：backend ｜ WBS：B1（0.5d）

## 解决的问题

B2（元数据补全）、B3（RAG 知识库）、B5（文献导入）、B8（导出）都要使用 embedding、向量库、PDF 抽取、文件上传、docx 生成能力。B1 一次性铺好依赖与配置位，后续模块直接复用，不重复安装/不各自写配置读取。

## 数据流（配置流）

```
.env ──load_dotenv──► config.py(Settings dataclass) ──► 各模块 import settings
  DEEPSEEK_API_KEY ─────────────► settings.deepseek_api_key ──► main.py /api/chat（现有）
  SILICONFLOW_API_KEY ──────────► settings.siliconflow_api_key ──► B3 embedding
  SILICONFLOW_BASE_URL ─────────► settings.siliconflow_base_url ──► B3 OpenAIEmbeddings
  EMBEDDING_MODEL ──────────────► settings.embedding_model ──► B3（默认 BAAI/bge-m3）
  VAULT_PATH / KB_DIR ──────────► settings.vault_path / kb_dir ──► B3/B4（默认推导待定）
  PORT ─────────────────────────► settings.port ──► uvicorn
```

## 接口清单（Settings 字段）

| 字段 | 默认值 | 用途 |
|---|---|---|
| deepseek_api_key | ""（.env） | LLM：DeepSeek，main.py 直连 |
| deepseek_base_url | https://api.deepseek.com | LLM base URL |
| port | 3001 | uvicorn 端口 |
| siliconflow_api_key | ""（.env） | embedding 服务 key（B3） |
| siliconflow_base_url | https://api.siliconflow.cn/v1 | embedding base URL（OpenAI 兼容） |
| embedding_model | BAAI/bge-m3 | embedding 模型 |
| vault_path | "" | vault 根目录（未配置，B3 定默认） |
| kb_dir | "" | .kb 元数据目录（未配置） |

## 关键决策

1. **LangChain 拆包，不装大包**：langchain 0.3+ 官方架构，核心在 langchain-core，集成独立成包。只装检索侧需要的 4 个包（core/openai/text-splitters/chroma），避免拖入几十个无用集成。`langchain-deepseek` / `langchain-community` 不需要——LLM 层不进 LangChain。
2. **LLM 不走 LangChain**：DeepSeek 是 OpenAI 兼容协议，现有 main.py 用 openai SDK 直连（`AsyncOpenAI(base_url=deepseek)`）。B7 做 RAG 注入只是往 system prompt 拼检索结果，SSE 协议逐字节不变（PRD 9.2 硬性要求）。LangChain 只承担 embedding/分块/向量库（检索侧）。
3. **保持 dataclass + dotenv**：与现有 3 字段一致、frozen 不可变、零新依赖。未引入 pydantic-settings（后续配置变复杂再迁移）。
4. **版本约束 `>=x,<y`**：语义化区间而非 pin 死，pip 自动解析兼容版本，兼顾稳定与可升级。
5. **VAULT_PATH/KB_DIR 只铺位不拍板**：vault 是用户自选文件夹，默认推导逻辑与前端首次启动引导联动，交给 B3/B4 决策，避免过度设计。

## 验证结果

- 8 个新依赖安装成功（pip 清华镜像），无版本冲突
- langchain_openai / langchain_text_splitters / langchain_chroma / langchain_core、pypdf / python-docx / bs4 / multipart 全部可导入
- `/health`、`/`、`/api/chat`（SSE 错误分支）验证通过，现有代码零影响

见 `docs/面试问答.md` 中 B1 相关条目。

# 模块说明：B2 元数据补全服务（backend/app/metadata.py）

> 交付时间：2026-08-12 ｜ 分支：backend ｜ WBS：B2（1d）

## 解决的问题

文献导入时自动补全元数据：输入 DOI 或 arXiv ID → 调免费公开 API → 返回规范化字段。B5 的 `POST /api/documents` 会调用本模块，失败时走手动录入。

## 数据流

```
identifier（"10.xxxx/xxx" 或 "2401.xxxxx"）
   │ detect_id_type()（正则：DOI / arXiv 新老版 / none）
   ├─ doi ─► GET api.crossref.org/works/{doi} ─► JSON message ─► normalize_crossref()
   └─ arxiv ─► GET export.arxiv.org/api/query?id_list={id} ─► Atom XML ─► normalize_arxiv()
                                   │
                        统一返回规范 dict，失败一律 {}
```

## 接口清单

| 函数 | 签名 | 说明 |
|---|---|---|
| `detect_id_type` | `(str) -> Literal["doi","arxiv","none"]` | 正则识别标识符类型 |
| `fetch_metadata` | `async (str) -> dict` | 统一入口（B5 只调这个） |
| `fetch_by_doi` | `async (str) -> dict` | Crossref GET + 规范化 |
| `fetch_by_arxiv` | `async (str) -> dict` | arXiv Atom XML + 规范化 |
| `normalize_crossref` / `normalize_arxiv` | `(Any) -> dict` | 纯函数：API 原始响应 → 规范 dict |
| `_parse_authors_crossref` / `_parse_author_name` / `_parse_year` | 辅助 | 作者/年份解析 |

**输出字段**（对齐 PRD 5.4 literature.json）：`title, authors[{given,family}], year, venue, volume, issue, pages, doi, arxivId, keywords`

## 关键决策

1. **httpx 异步客户端，不用 requests**：FastAPI 全链路 async，httpx 不阻塞事件循环；requests 同步会卡住并发。已显式声明进 requirements（直接依赖显式化）。
2. **作者存结构化 `[{given, family}]`**：为 B8 导出格式化铺路（GB/T 7714 要"姓 名缩写"、APA 要"Smith, J."，前提是姓名有边界）。arXiv 名字字符串按"最后 token 为 family"解析；Crossref 直接有 given/family；机构作者名放入 family。
3. **bs4 解析 arXiv Atom XML**：命名空间前缀（arxiv:journal_ref）用"tag name endswith 前缀"匹配，兼容两种写法。
4. **失败兜底统一返回 `{}`**：网络错误/404/超时/解析失败一律空 dict，调用方 `if not metadata:` 走手动录入。增强功能失败不打断主流程。
5. **Crossref 带 `mailto` 参数**（polite pool）：限流更宽松的行业惯例。
6. **CLI 入口**（`python -m app.metadata <id>`）：演示/调试/面试 demo 用。

## 验证结果

- 纯函数断言：类型识别（doi/arxiv/老版/乱输）、作者解析、Crossref 规范化全过
- 真实 arXiv `1706.03762` → Attention Is All You Need（year=2017，keywords=[cs.CL]）
- 真实 DOI `10.1109/CVPR.2016.90` → Deep Residual Learning（year=2016，venue=CVPR 全称，pages=770-778）
- 兜底：不存在的 DOI → `{}`；非识别格式 → `{}`

## 踩坑记录

- **arXiv API 301 重定向**：`http://export.arxiv.org` 现在跳转 https，而 **httpx 默认不跟随重定向**（`follow_redirects=False`，与 requests 的默认 True 相反）→ 换 https URL + 显式 `follow_redirects=True`。
- **10.48550 前缀不在 Crossref**：arXiv 的 DOI（10.48550/...）由 **DataCite** 注册，Crossref 查会 404。这是预期行为，兜底处理即可。

# 模块说明：B3 知识库核心（backend/app/kb.py）

> 交付时间：2026-08-13 ｜ 分支：backend ｜ WBS：B3（1.5d）

## 解决的问题

RAG 的地基：把笔记/PDF 文本变成可检索的向量索引，提供**写入（幂等 upsert）、删除、检索（支持单篇限定）**。B6 扫描 vault 时调 upsert，B7 问答时调 retrieve。

## 数据流

```
笔记纯文本 / PDF 文件
   │  extract_pdf_pages()（pypdf 逐页抽取，保留页边界）
   ▼
split_pages()：RecursiveCharacterTextSplitter(500/50，分隔符含中文标点)，页内分块
   │  每块带 metadata：page / docType(note|paper) / docId / title
   ▼
upsert_document()：先 delete(where=docId) → OpenAIEmbeddings(SiliconFlow, bge-m3) → Chroma.add
   ▼
backend/vault/.kb/chroma_db/（持久化，可删可重建，见 ADR-0001）
   │
retrieve(query, doc_id=None, top_k=5)：similarity_search(filter)
   ├─ 全局：filter=None
   └─ 单篇：filter={"docId": doc_id}
   ▼
返回 LangChain Document 列表（page_content + metadata）→ B7 注入
```

## 接口清单

| 函数 | 签名 | 说明 |
|---|---|---|
| `extract_pdf_pages` | `(str\|Path) -> list[str]` | pypdf 逐页抽取 |
| `split_pages` | `(list[str]) -> list[Document]` | 页内分块，空块过滤 |
| `upsert_document` | `(doc_type, doc_id, title, pages=None, text=None) -> int` | 幂等写入，返回块数；doc_type ∈ note/paper |
| `delete_document` | `(doc_id) -> None` | Chroma delete where docId |
| `retrieve` | `(query, doc_id=None, top_k=5) -> list[Document]` | 相似度检索 |
| `get_collection` | `() -> Chroma` | 懒加载单例 |
| `_default_vault_path` / `_kb_root` / `_chroma_dir` | 路径推导 | 见 ADR-0001 |

## 关键决策

1. **vault 默认路径（ADR-0001）**：`VAULT_PATH` 未配置 → `backend/vault`（开发期）；`.env` 优先；发布期由前端交互引导用户指定后写入。`KB_DIR` 未配置 → `{vault}/.kb`，Chroma 存 `{vault}/.kb/chroma_db`。
2. **同步核心 + 调用方 to_thread**：langchain embedding/Chroma 仅同步 API，kb.py 保持纯同步；async 路由（B5/B7）用 `anyio.to_thread` 包一层，不阻塞事件循环。
3. **页级分块**：块不跨页，metadata.page 准确——RAG 回答要附来源页码（PRD 5.6）。代价：页末块可能不足 500 字。
4. **幂等 upsert**：先删旧块再 add，B6 重复索引结果一致。
5. **单例懒加载**：首次调用 `get_collection()` 才建立 Chroma 连接；**初始化校验 SILICONFLOW_API_KEY**，缺失即抛错（明确失败），B7 的降级逻辑在调用侧。
6. **中文标点分隔符**：`["\n\n","\n","。","！","？","；","，"," ",""]`，块边界落在句号处。
7. **元数据约定**（PRD 5.4）：`docType / docId / page / title`，全部 Chroma 基础类型。

## 验证结果（真实 embedding，SiliconFlow API）

- 纯函数：分块页码/空块过滤/中文标点边界；空白 PDF 抽取 2 页不崩
- 全链路：upsert 2 篇中文文档 → 语义查询命中正确文档 → 单篇限定（where 过滤）生效 → delete 后检索不到
- `.kb` 结构确认：`vault/.kb/chroma_db/chroma.sqlite3`（chromadb 1.x 直接存 sqlite3，无嵌套 .chroma）

## 范围边界

- **retrieve 是查询能力**（返回 Document 列表即止）；**B7 的检索注入**（检索结果 → system prompt、降级、来源标注）由用户亲手实现。

# 模块说明：B4 vault 文件 API（backend/app/routers/fs.py + app/vault.py）

> 交付时间：2026-08-14 ｜ 分支：backend ｜ WBS：B4（1d）

## 解决的问题

开发期浏览器无法直接读写本地文件（File System Access API 仅 Chromium 且要授权），后端提供 vault 内文件读写的 HTTP 兜底；F1 的 `HttpFsAdapter` 调它，发布期换 Tauri 原生 fs 插件，业务代码零改动（PRD 8.3）。

## 接口清单（`/api/fs/*`，path 为 vault 内相对路径）

| 方法 | 路径 | body | 说明 |
|---|---|---|---|
| GET | `/api/fs/list?path=` | — | 列目录 → `{entries: [{name, isDir, path}]}`，目录优先排序 |
| GET | `/api/fs/read?path=` | — | 读文本（utf-8）→ `{content}` |
| GET | `/api/fs/file?path=` | — | 二进制流（PDF），FileResponse |
| POST | `/api/fs/write?path=` | `{content: str}` | 创建/覆盖一体，原子写 |
| POST | `/api/fs/mkdir?path=` | — | 建目录（多级） |
| DELETE | `/api/fs/delete?path=` | — | 删文件/空目录（非空拒绝） |
| GET | `/api/fs/exists?path=` | — | → `{exists}` |

错误约定：越界 403 / 不存在 404 / 类型不匹配或失败 400 / 写入失败 500，body 为 `{"detail": ...}`。

## 关键决策

1. **防目录穿越（核心安全）**：`(vault / relative).resolve()` 后必须 `is_relative_to(vault)`。`resolve()` 折叠 `..` 与符号链接得真实路径，`is_relative_to` 做包含判断——不能用 `str.startswith`（`/vault/../etc` 字符串前缀不匹配但语义越界）。
2. **原子写**：先写 `name.tmp` 再 `os.replace`。自动保存 600ms 防抖高频写，直接写文中途崩溃留半截文件；os.replace 同卷原子（旧/新文件二选一完整）。
3. **路由模块化**：B4 起建 `app/routers/` 包，main.py `include_router(prefix="/api/fs")`。B5-B8 陆续挂载各自 router，main.py 不再膨胀。
4. **路径推导下沉 `app/vault.py`**：kb.py 的路径函数挪为 `default_vault_path()/kb_root()/chroma_dir()` 公共函数，kb/fs/B5 共用一处定义。
5. **read（文本 JSON）与 file（二进制流）分离**：PDF 不走 base64 包装（膨胀 33% + 前端解码）。
6. **delete 只删空目录**：rmdir 保守策略，防误删整棵目录树；递归删除由调用方按需实现（MVP 无此场景）。
7. **write 用 POST 而非 PUT**：创建/覆盖一体、path 在 query，无资源定位语义，POST 更简单。

## 验证结果

- 全流程：list 根 → mkdir → write（含中文路径/换行）→ read 回读 → exists → list 子目录 → file 二进制下载（431 bytes）→ delete
- **穿越攻击专项**：`../config.py`、`..%2F..%2Fconfig.py`、`..%2F..%2F..%2FWindows%2Fwin.ini` → 全 403
- 错误分支：不存在 404、read 二进制 400、read 目录 400、非空目录删除 400、GET 打 delete 405、非法 body 422
- kb.py 回归：路径函数重构后 upsert→query→delete 正常

## 踩坑记录

- **Git Bash 里 curl 直接传中文字面量会损坏编码**（GBK 控制台），`--data-urlencode "path=文献"` 实际创建了乱码目录 → 验证改用 httpx（正确 UTF-8 编码）或 python quote 生成编码 URL。与后端无关，是测试工具链问题。

# 模块说明：B5 文献导入与管理 API（app/literature.py + app/routers/documents.py）

> 交付时间：2026-08-14 ｜ 分支：backend ｜ WBS：B5（1d）

## 解决的问题

文献线主节点：PDF 导入（上传 → 存文件 → 元数据补全 → 建索引 → 入库）与管理（列表/删除）。B2 元数据补全 + B4 文件能力在此汇合。

## 数据流

```
UI 组件（SiderBar / Editor / useNotes）
   │  调用（同步签名，对外不变）
   ▼
useDataStore（Zustand 内存缓存 = 响应式数据源）
   │  loadAll：list('笔记') → 逐个 read() → 内存
   │  saveNote：write(路径, content)（fire-and-forget）
   │  deleteNote：delete(路径)
   ▼
StorageAdapter 接口（src/services/storage/types.ts，★用户亲手实现）
   ▼
HttpFsAdapter（src/services/storage/http-fs-adapter.ts）
   │  fetch + encodeURIComponent + 解包 + 非 2xx 抛 Error(detail)
   ▼
GET/POST/DELETE /api/fs/*（B4）→ vault 文件

---

multipart（file + doi/arxivId）
  │
  ▼ POST /api/documents
① 校验 .pdf 后缀 ② 流式写盘（{lit_id}_{清洗原名}.pdf，≤50MB）
③ metadata.fetch_metadata() 补全（失败 title 占位） ④ DOI/arXiv 重复检测 → 409
⑤ kb.extract_pdf_pages + upsert_document（to_thread；失败降级）
⑥ literature.json 原子写 → 201

GET /api/documents → literature.json → 列表（importedAt 倒序）
DELETE /api/documents/{id} → PDF 文件 + kb 索引 + json 三连清理
```

## 接口清单

**StorageAdapter（types.ts）**：`read/write/list/mkdir/delete/exists` 6 方法，path 为 vault 相对路径（空串=根），全异步。

| 方法 | 对应后端 | 返回 |
|---|---|---|
| `list(path)` | GET /api/fs/list | `Promise<FsEntry[]>`（解包 entries） |
| `read(path)` | GET /api/fs/read | `Promise<string>`（解包 content） |
| `write(path, content)` | POST /api/fs/write | `Promise<void>` |
| `mkdir(path)` | POST /api/fs/mkdir | `Promise<void>` |
| `delete(path)` | DELETE /api/fs/delete | `Promise<void>` |
| `exists(path)` | GET /api/fs/exists | `Promise<boolean>`（解包 exists） |

**useDataStore 改动**：`loadAll` 从空操作变为"扫描 vault/笔记/*.md 读入内存"；`saveNote` 写文件+更新内存；`deleteNote` 删文件+更新内存。对外签名不变（`saveNote: (note) => number` 仍同步），useNotes/编辑器/SiderBar 零改动。

## 关键决策

1. **接口先行 + 依赖倒置**：业务依赖抽象不依赖实现；工厂 `createStorageAdapter()` 是唯一出口，换实现只改一处（src/services/storage/index.ts）。
2. **saveNote 保持同步签名，写文件 fire-and-forget**：改 async 要动所有调用方（编辑器 600ms 防抖、SiderBar 新建），违背"UI 零改动"。内存更新同步完成（响应式即时），文件写入异步执行、失败 console.error。代价：写失败用户无感知，F2 可加写队列与失败提示。
3. **文件名在新建时定死，不随 title 变化**：editor 自动保存会把 title 改成正文第一行（`firstLine.slice(0, 30) || 'Untitled'`），若文件名=title，每次改首行笔记就"搬家"（删旧建新）、同标题互相覆盖。故新建时按当时标题定文件名（重名自动加 ` (2)` 后缀），此后 title 变化只更新内存不搬文件。F2 frontmatter 后文件内 title 为权威，此问题彻底解决。
4. **文件内容暂存 Tiptap HTML，扩展名 .md**：过渡形态——F2 用 tiptap-markdown 序列化 + frontmatter 时迁移，届时 loadAll/saveNote 内部改格式，UI 仍零改动。
5. **loadAll 失败降级空列表**：后端未启动时 list 抛错 → 尝试 mkdir 也失败 → notes=[]，UI 不崩（console.warn）。
6. **接口不提前加 `readBinary`**（读 PDF 二进制，对应 GET /api/fs/file）：F5 才需要，YAGNI——接口演进是允许的，不提前加用不到的方法。
7. **集合仍为内存态**：collections.json / 集合目录结构是 F2 内容，F1 不越界。

- `npx tsc -b` 通过；`npm run build`（tsc + vite）通过

# 模块说明：F2 笔记 Markdown 化（frontend/src/lib/note-file.ts + useDataStore/editor 改造）

# 模块说明：F2 bugfix —— gray-matter 浏览器 Buffer 崩溃（替换为 js-yaml@4 自研 frontmatter 工具）

> 修复时间：2026-08-14 ｜ 分支：frontend ｜ 现象：保存笔记只有 frontmatter 没有正文，控制台 `ReferenceError: Buffer is not defined`

## 根因（用户报错 + 源码定位）

- 报错栈：`serializeNote (note-file.ts:50) → matter.stringify`；`utils.js:36`
- gray-matter 的 `lib/utils.js toBuffer`（L35-37）：`return typeof input === 'string' ? Buffer.from(input) : input` —— **直接使用全局 `Buffer`**，浏览器没有全局 Buffer → 非空内容保存必抛 ReferenceError
- **为什么"新建"能用**：gray-matter 的 `matter()` 对**空字符串短路返回**（index.js L30-32 `if (input === '') return ...`），不触发 toFile/toBuffer——所以空 content 的新建笔记成功写入 frontmatter，非空 content 的自动保存崩溃。这解释了"文件里只有笔记名和集合信息"
- **为什么 js-yaml 不受影响**：js-yaml 的 buffer 引用（type/binary.js `require('buffer')`）经 Vite/esbuild 预构建安全 stub（`try { NodeBuffer = require_browser_external_buffer().Buffer } catch {}`），binary 类型自动降级不抛错
- **为什么此前测试没发现**：Node 环境有全局 Buffer；浏览器模拟验证只测了 parse 路径（`matter(raw)` 对非空输入也走 toBuffer…… 实际 verify-prebundle 测的是 load 路径），**漏测了 stringify 路径**

## 修复方案（决策：自研替换而非 polyfill）

| 方案 | 内容 | 取舍 |
|---|---|---|
| A. Buffer polyfill | 装 `buffer` 包 + 入口注入 `globalThis.Buffer` | 改动最小但引入 ~30KB polyfill + 全局污染 |
| B. 自研 frontmatter 工具 | `src/lib/frontmatter.ts` 用 js-yaml@4 直接 parse/stringify（~50 行），复刻 gray-matter 格式 | **采纳**：无全局污染、bundle 反而减小 275KB（去掉 gray-matter 外壳依赖）、js-yaml 4 浏览器零 Buffer 引用（已核验 dist/js-yaml.mjs） |

**新文件**：`src/lib/frontmatter.ts` —— `stringifyFrontmatter(content, data)` / `parseFrontmatter(raw)`，格式与 gray-matter 输出兼容（`---\n...\n---\n正文`，close 后吃掉一个换行，正文尾部补 \n），YAML 解析失败容错（data={}，正文保留，不阻断加载）。

**依赖变化**：`- gray-matter`，`+ js-yaml@4`（直接依赖）+ `@types/js-yaml`（dev）。

## 验证结果

- 纯函数 round-trip 21/21（Node）：非空 content 全字段、空 content、无 frontmatter、Obsidian 空行风格、YAML 损坏容错、旧格式（js-yaml 3 输出）兼容、特殊字符、round-trip 稳定
- **浏览器环境验证**：vite prebundle 的 js-yaml@4 → dump/load/完整链路全部通过（此前的 BUG 路径）；rolldown browser 平台产物零 Buffer 引用（3 个匹配均为 `pairBuffer` 局部变量）
- 集成 e2e 7/7（真实后端）：新建 → 自动保存非空正文 → 文件含正文 → 刷新恢复 → backendOnline
- `tsc` + `vite build` 通过；bundle 1,428KB → 1,153KB（-275KB）；buffer externalize 警告消失

## 踩坑记录（新增）

- **依赖的浏览器兼容性必须按"实际运行路径"验证**：gray-matter 空/非空输入走了完全不同的代码路径（短路 vs toBuffer），只测"能用"的路径会漏掉崩溃路径。教训：**验证要覆盖调用的全部输入形态**（空值、边界值），尤其是"看似正常"的场景（新建成功）背后可能藏着不同的代码路径。

# 模块说明：F3 侧边栏/列表文件模式改造（renameNote + refreshFromDisk 30s 轮询）

> 交付时间：2026-08-14 ｜ 分支：frontend ｜ WBS：F3（1.5d）

## 解决的问题

F1/F2 已把数据源从 useLiveQuery 换成"文件扫描 + 内存状态"（WBS 的这部分提前完成）。F3 补齐剩余能力：①**笔记重命名**（用户此前反馈"笔记名不能更改"）；②**外部修改感知**（Obsidian/VS Code 直接改 vault 文件后，前端 30s 内自动同步）；③title 语义理清。

## 关键决策

1. **title 权威化（重命名能生效的前提）**：原 editor 自动保存用正文第一行覆盖 title（`firstLine.slice(0,30)`），若加侧边栏重命名，用户改名后下次编辑就被第一行覆盖。方案：自动保存**不再计算/覆盖 title**，title 只由新建（"新笔记"）与重命名决定，frontmatter title 成为唯一权威。代价：失去"第一行即标题"的旧 UX（用户已确认接受）。
2. **重命名只改 frontmatter title，文件名不动**（F1 决策延续）：文件名是存储标识（新建时定死防"搬家"），title 是显示名。改文件名会连锁引发同名冲突、idToPath 重建、后端索引失效（B6 按文件建索引）。MVP 改 title 已满足需求。
3. **轮询 = `refreshFromDisk(skipNoteId?)`，30s 全量重读 + 跳过正在编辑的笔记**：直接 loadAll 覆盖会让"用户正在输入（600ms 防抖窗口内）"的笔记被磁盘旧版覆盖 → 输入丢失。skipNoteId 对应笔记保留内存值（编辑器 doc 独立于内存 notes，自动保存最终会写回，无丢失）。轮询失败（后端离线）静默保持现状，不覆盖 backendOnline 警告。

## 接口清单

| 函数 | 签名 | 说明 |
|---|---|---|
| `renameNote` | `(id, newTitle) => void` | 内存立即更新 + 重写文件（frontmatter title；同步签名，写文件 fire-and-forget，失败置离线） |
| `refreshFromDisk` | `(skipNoteId?) => Promise<void>` | list + 逐文件 read/parse → 与内存合并：外部修改更新、外部新增分配新 id、外部删除移除、skipNoteId 保留内存值；失败静默 |

**UI 改动**：
- SiderBar：笔记行 hover 新增**重命名按钮**（Pencil 图标 → prompt 输入 → renameNote），未分类组与集合组两处
- Home：`setInterval(30s)` 调 `refreshFromDisk(activeNoteId)`，卸载清理；activeNoteId 变化重建定时器
- editor：自动保存去掉 title 计算（保留 existingNote.title）

## 验证结果

- 集成 e2e 8/8（真实后端）：rename 文件 title 更新/文件名不变/内存更新；refresh 外部修改同步、**skipNoteId 保护**（正在编辑的笔记保留内存值）、外部新增同步、外部删除同步
- `npx tsc -b` 通过；`npm run build` 通过

## 面试要点

见 `docs/面试问答.md` F3 条目（②Q4、③Q8、④Q8）。

## 范围边界

- 集合重命名不在本次（需同步重写所有该集合笔记的 frontmatter，留待需要时）
- 外部修改感知是 30s 轮询粒度（内容级），M2 换 watchdog + SSE 通知

# 模块说明：B5 文献导入与管理 API（app/literature.py + app/routers/documents.py）

> 交付时间：2026-08-14 ｜ 分支：backend ｜ WBS：B5（1d）

## 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/documents` | multipart：`file` + 可选 `doi`/`arxivId`；201 返回 entry |
| GET | `/api/documents` | `{entries: [LiteratureEntry...]}`，importedAt 倒序 |
| DELETE | `/api/documents/{lit_id}` | 三连清理；404 不存在 |

`LiteratureEntry` 字段（对齐 PRD 5.4）：`id, title, authors[{given,family}], year, venue, volume, issue, pages, doi, arxivId, pdfPath(vault 相对), status, collectionIds, tags, importedAt`

## 关键决策

1. **数据层/路由层分离**：literature.py 只管 json 增删查（原子写 + 损坏重建），documents.py 编排 HTTP/文件/补全/索引。
2. **文件名 = `{lit_id}_{清洗原名}.pdf`（方案 C）**：ID 保证唯一与关联、清洗后原名保证 vault 可读性（用户决策，理由见 docs/kb 系列讲解的"系统标识 vs 用户标签"）。
3. **清洗规则**：取 basename、`\/:*?"<>|` 与控制字符替换为 `_`、限长 100 字符、空则 untitled——上传文件名不可信（路径注入/非法字符/超长）。
4. **重复检测**：DOI（大小写不敏感）/ arXiv ID 精确匹配 → 409（P0 要求）。
5. **双重降级**：元数据补全失败 → title 占位照常入库；索引失败（embedding/key/网络）→ 跳过索引。增强功能失败不阻断主流程（B2 的 `{}` 约定在此兑现）。
6. **流式写盘**：1MB 块边读边写，50MB 上限——不把整个文件读进内存。
7. **to_thread 调度**：extract_pdf_pages（CPU）+ upsert（embedding 网络 IO）同步函数经 `anyio.to_thread.run_sync` 调度（ADR-0002）。**注意 run_sync 只接受位置参数**（本次踩坑）。

## 验证结果（真实 arXiv PDF：1706.03762）

- 带 arxivId 导入：title/authors/year 全自动补全，201；文件名 `{id}_attention_is_all_you_need.pdf`
- kb 全局检索 3 条命中（page 2/4 论文原文）、单篇限定 2 条
- 重复导入 409；无标识符导入 title 占位（文件名 stem）；非 PDF 400；50MB 上限（代码路径）
- DELETE 三连：文件删、kb 检索 0 条、literature.json `[]`、无 .tmp 残留

## 踩坑记录

- **`anyio.to_thread.run_sync` 不接受关键字参数**：`run_sync(func, ..., pages=pages)` 抛 `TypeError: run_sync() got an unexpected keyword argument 'pages'` → 全部改位置参数（upsert_document 第 4 个位置参数即 pages）。
- **uvicorn 未加 `--reload` 导致修复不生效**：验证时改代码后服务仍跑旧代码，排查半天才确认是没重载——dev 启动命令必须带 `--reload`（CLAUDE.md 常用命令已如此约定）。

# 模块说明：B6 索引管理与变更检测（app/indexer.py + app/routers/kb_api.py）

> 交付时间：2026-08-15 ｜ 分支：backend ｜ WBS：B6（1d）

## 解决的问题

vault 是外部可见可编辑的文件夹（Obsidian/VS Code），文件被直接改动后索引过期。B6 提供增量刷新与状态查询，并在后端启动时自动全量扫描（PRD 5.5）。

## 核心机制：index_state.json（元数据的元数据）

```json
{
  "lastScan": "2026-08-15T13:22:20",
  "note":  {"笔记/xx.md": {"docId": "笔记/xx", "mtime": 1234567, "size": 890, "chunks": 5}},
  "paper": {"文献/{id}.pdf": {"docId": "{lit_id}", "mtime": ..., "size": ..., "chunks": 30}}
}
```

## 接口清单

| 方法 | 路径 | body | 说明 |
|---|---|---|---|
| GET | `/api/kb/status` | — | `{chunks, indexedNotes, indexedPapers, unindexedFiles[], lastScan}` |
| POST | `/api/kb/refresh` | `{"force": bool}` | 增量（默认）/ 全量重建 → 报告 `{scanned, indexed, deleted, skipped, errors[], totalChunks}` |

## 关键决策

1. **mtime+size 比对做增量，不用内容 hash**：文件系统元数据 O(1) 获取，千级文件无 CPU 压力；hash 每文件全读一遍。代价：手动改 mtime 可伪造——个人本地场景可接受（成本换精度的取舍）。
2. **笔记 docId = 相对路径去 .md**：PRD 5.4 笔记 frontmatter 无 id 字段，路径是天然稳定键；重命名 = 新路径 = 旧索引清理 + 新索引。
3. **文献权威源是 literature.json 而非文件扫描**：vault/文献 下未入库 PDF 不自动收编（防误索引）；literature 有记录但 state 无 → refresh 补索引（覆盖 B5 索引降级场景）。
4. **force 全量 = 按旧 state 全部 delete 再重建**：解决 state 损坏/索引逻辑升级；避免 Chroma 残留旧块。
5. **state 原子写 + 损坏重建**：丢失可 force 重建，非用户数据。
6. **启动扫描用 lifespan**：`app = FastAPI(lifespan=lifespan)`，启动时 to_thread 跑 scan_and_index，**失败只警告不阻断启动**（vault 缺失/key 缺失都继续起服务）。
7. **frontmatter 剥离**：正文进向量、元数据不进；title 取 frontmatter 缺省文件名。pyyaml 显式声明进 requirements（后端索引侧与前端 gray-matter 解析同一文件）。

## 验证结果

- 启动自动扫描：2 篇笔记自动入索引，title 取自 frontmatter（非文件名）
- 幂等：连续 refresh 全 skipped，totalChunks 不变
- 增量：修改笔记 → indexed=1 且新段落检索命中；新增 → 补索引
- 消失清理：删笔记/文献 → deleted 计数正确、检索归零、status 归零
- force 全量：旧索引清除后重建
- unindexed 检测：手动放 .md 不进 state → status.unindexedFiles 列出 → refresh 后消除
- 文献幂等：导入后 refresh skipped

## 已知问题（偶发，未复现成功）

- chromadb 1.5.9 + langchain-chroma 0.2.6 曾出现一次"删除后立即检索返回 page_content=None"的 pydantic 校验错误，8 轮删除-检索循环无法复现（0/8）——疑似 chroma 内部一次性时序状态，记录待观察；如复现考虑固定 chromadb 版本或升级 langchain-chroma。**后续已发生一次 chroma_db HNSW 索引损坏**（`Error loading hnsw index`，删除 chroma_db 重建解决）——与上述偶发疑似同源，chromadb 1.5.9 稳定性待观察。

# 模块说明：B5.1 导入时自动提取 DOI（metadata.extract_doi + documents.py 流程改造）

> 交付时间：2026-08-15 ｜ 分支：backend ｜ WBS：B5 增强（约 0.3d）

## 解决的问题

B5 补全机制是"用户主动给 DOI/arXiv 才查"——不填就不补全（真实案例：用户导入闭源期刊 PGFD-YOLO，未填 DOI，元数据全空、title 文件名占位）。增强后：**导入不带标识符时，自动扫描 PDF 首页文本提取 DOI → 触发补全**，拖入即得元数据。

## 数据流

```
写盘 → identifier = doi or arxivId（显式优先）
     → 为空时：to_thread extract_pdf_pages（抽文本）
              → metadata.extract_doi(前2页拼接) → 找到则 identifier = DOI
     → fetch_metadata(identifier)（补全）
     → 建索引：复用已抽的 pages（不重复抽取）
```

## 接口清单

| 函数 | 位置 | 说明 |
|---|---|---|
| `extract_doi(text) -> str \| None` | `app/metadata.py`（新，纯函数） | 三种形态：`doi.org/xxx` → `doi: xxx` → 裸 `10.xxxx/`（负向后顾 `(?<![\w.])` 防超链接误匹配）；尾部标点清洗（`.,;:)]}>'"`） |

**documents.py 流程**：identifier 为空时抽前 2 页文本提取 DOI；`pages` 缓存复用给索引阶段（避免大 PDF 抽两次）；提取失败/无 DOI → 静默降级 title 占位（延续 B2/B5 约定）。

## 关键决策

1. **显式 > 自动**：用户填了 DOI/arXiv 就绝不自动提取（显式标识符优先级不变）。
2. **只扫前 2 页**：DOI 几乎必在首页（标题下方），全篇扫描浪费；抽取结果缓存复用给索引。
3. **正则分层 + 清洗**：先精确形态（doi.org/doi: 前缀）再裸 DOI；字符集限定 `[A-Za-z0-9._;()/:+-]`（排除空白/中文/引号防贪婪），尾部 rstrip 标点（PDF 文本里 DOI 后常跟句号——"…130053." 的句号不能吞进 DOI）。
4. **失败降级**：假 PDF/扫描件抽不出文本 → 保持占位流程，不阻断导入。

## 验证结果

- 纯函数 9/9：doi.org 形态、doi: 形态（含中文冒号）、裸 DOI + 句号/逗号、无 DOI → None、空文本 → None、负数（-10.5）不误匹配
- 集成 8/8（真实后端 + 用户 PGFD-YOLO PDF，不带 identifier 导入）：**自动提取 `10.1016/j.jenvman.2026.130053`** → title 完整补全（非文件名占位）/year 2026/venue Journal of Environmental Management/作者 2 人 → 清理
- 回归：显式 DOI 导入 201 正常（优先级不变）

# 模块说明：F5 PDF 阅读器（Reader 组件 + pdfjs-dist 集成）

## 解决的问题

F4 已能"导入→列表→详情→删除"，但 PDF 打不开。F5 补齐「读」这环：**canvas 渲染 + 文字层 + 翻页/缩放/页码 + 划词浮层**，其中划词三操作（转笔记引用 / 问 AI / 复制）是工作台灵魂动作（PRD 4.3）。

## 数据流


## 接口清单

| 文件 | 内容 |

| `src/components/Reader/selection-toolbar.tsx`（新） | `SelectionToolbar`：划词浮层三按钮 |
| `src/components/Reader/cite-picker.tsx`（新） | `CitePicker`：转笔记目标选择（追加/新建） |

| `package.json` | + `pdfjs-dist@6.2.108` |

## 关键决策

1. **PDF 二进制直接 fetch /api/fs/file，不扩展 StorageAdapter**：StorageAdapter.read 是文本读（utf-8），PDF 是二进制，塞进去要 base64 包装（膨胀 33% + 解码）。后端 B4 已提供 `/api/fs/file`（FileResponse 二进制流），F5 的 services/pdf.ts 直接 fetch 它——正是 F1 决策 6「readBinary 留到需要时再加」的 YAGNI 兑现。
2. **worker 用 new URL(..., import.meta.url)**：pdf.js 解析在 Web Worker 独立线程；Vite 下写死字符串路径 build 报错，new URL 让打包器输出独立 asset（PRD 9.4 点名的坑）。
3. **text layer 用透明 span 覆盖 canvas**：canvas 位图文字无法被浏览器选中/复制；TextLayer 生成绝对定位透明 span，文字可选可复制，选中反馈靠 ::selection 半透明背景。
4. **划词 mouseup 即存 state**：点击菜单按钮会清空浏览器 selection，故 mouseup 时就把 text + 坐标存进 React state，按钮回调读 state 而非实时 selection。
5. **渲染竞态保护（cancelled 标记）**：pdf.js 渲染异步，快速连翻页时旧页可能晚返回 → effect cleanup 置 cancelled + renderTask.cancel()，丢弃过期结果。
6. **高清屏 devicePixelRatio**：canvas 物理像素 = CSS 尺寸 × dpr，否则 Retina 下发虚。
7. **转笔记引用写纯 Markdown [[cite:id]]**：F5 先落 blockquote + 页码 + `[[cite:id]]` 文本（源文件可读），F6 引用系统再渲染成徽章。
8. **问 AI 只做预填通道**：F5 打开面板 + 预填选中文本；单篇上下文限定、解释/翻译/总结三子项是 F7「AI 面板适配」内容（用户已确认边界）。

## 验证结果

- `npx tsc -b` 通过
- `npx vite build` 通过：`dist/assets/pdf.worker-*.mjs (2.22MB)` 确认 worker 正确打包为独立 asset
- 范围说明：PDF 渲染/划词需在浏览器 + 后端真实 PDF 上人工验收（sandbox 无法跑浏览器交互）

## 面试要点

见 `docs/面试问答.md` F5 条目（①Q8、②Q7、③Q9、④Q9、⑤Q9）。

## 踩坑记录

- **RenderParameters.canvas 是必填项**：pdfjs-dist 6.x 类型里 `canvas: HTMLCanvasElement | null` 必填、`canvasContext` 才是可选——照旧示例只传 canvasContext 报 TS2345。改用 `canvas` 参数 + transform（dpr 缩放）更简洁。

- **vite build 在受限 shell 下 spawn EPERM + tailwind oxide UTF-8**（F1 已记录）：非代码问题，需 danger-full-access 或用户终端跑。

# 模块说明：F6 引用系统 UI（Cite 内联节点 + 参考文献列表）

> 交付时间：2026-08-15 ｜ 分支：frontend ｜ WBS：F6（2d）

## 前置调研结论（先纠正 F2 一个误判）

- 用户要求"优先升级 tiptap-markdown"。查 npm：**latest 就是 0.9.0**，无更高版本可升级。
- 深挖 0.9.0 dist 源码发现：**它支持自定义节点序列化**，入口不是 PRD 假设的 `extendMarkdown`，而是让节点扩展在 `addStorage()` 里返回 `{ markdown: MarkdownNodeSpec }`（`index.d.ts` 里的 `MarkdownNodeSpec`/`MarkdownMarkSpec` 类型，`MarkdownSerializer.nodes` 会优先采用扩展的 `storage.markdown.serialize`）。
- 因此 F2 的"0.9.0 无 nodes/marks 自定义入口"结论是**误判**（当时只 grep 了 `extendMarkdown` 字符串）。F6 直接用现成机制，无需自写序列化器。

## 解决的问题

F5 划词转笔记已把引用写成 `[[cite:id]]` 纯文本，但编辑器里它还是普通文本：不能点击跳转、不显示"作者+年份"徽章、笔记尾部没有参考文献列表。F6 打通引用系统 UI：**引用标记 → 徽章渲染 + 点击跳转 + 序列化 round-trip + 笔记尾参考文献列表**（反向引用视图 F4 已前瞻实现，本次复用）。

## 关键决策

1. **引用是 node 不是 mark**：mark 修饰文本（加粗/斜体），引用徽章是独立语义单元、原子不可编辑、要携带 `id` 属性 → inline + atom node。
2. **`[[cite:id]]` wiki-link 语法 + markdown-it inline rule**：正则匹配 `[[cite:...]]` 渲染成 `<span data-cite>`，序列化/反序列化都精确，源文件可读（PRD 4.5）。
3. **serialize 输出与 F5 写入格式一致**：F5 已写 `[[cite:id]]`，F6 解析成徽章后保存再写回 `[[cite:id]]`，编辑不破坏引用（round-trip 无损）。
4. **徽章显示"作者+年份"查文献库**：NodeView 里 `useLiteratureStore` 查 id；缺失 fallback 显示 `cite:id` 本身（引用不失效）。
5. **参考文献列表简化格式**（用户决策）：前端只做"编号 + 作者 + 标题 + 年份 + 期刊"，完整 GB/T 7714 标点规则由后端 B8（用户亲手实现）提供后前端对接。
6. **点击切文献模式 + 选中**（用户决策）：跳转看完整元数据与反向引用。

- **F2 的"无自定义入口"是误判**：只 grep 了 `extendMarkdown` 字符串就下结论，实际入口是 `addStorage().markdown`（`getMarkdownSpec` 读 `extension.storage?.markdown`）。教训：探测第三方扩展能力要看**消费方代码**（序列化器怎么读扩展），而不是按 PRD 假设的关键词搜索。

# 模块说明：F7 AI 面板适配（全局/单篇问答 + 划词提问三子项）

> 交付时间：2026-08-16 ｜ 分支：frontend ｜ WBS：F7（1d，前端最后一项）

## 解决的问题

F5 的「问 AI」只做"打开面板+预填"；AI 面板的对话走任务模式（默认 summarize），没有 RAG 上下文概念。F7 补齐三种问答能力（B7 已就绪，协议：对话模式请求体加可选 `docId`）：**全局问答**（RAG 全库检索）/ **单篇问答**（docId 限定当前文献）/ **划词提问**（解释/翻译/总结），复用现有 SSE 打字机零改动。

## 数据流

```
全局问答：AIPanel 对话（不选任务按钮）→ fetchAiResponse(messages, ..., docId=undefined)
          → 后端 B7 全局 RAG 检索 → system prompt 注入 → SSE 打字机
单篇问答：docId = useLiteratureStore.readerId（正在阅读的文献）
          阅读器工具栏「问 AI」→ 打开面板（上下文条显示「单篇：文献标题」）
          → 后端 where={"docId": readerId} 限定检索
划词提问：划词浮层「问 AI」→ 展开三子项（解释/翻译/总结）→ prefillAiTask(type, text)
          → 面板打开 + 自动发送对话模式消息（指令 + 选中文本，带 docId）
```

## 接口清单

| 文件 | 改动 |
|---|---|
| `services/ai.ts` | `fetchAiResponse`：`taskType` 改为可选（undefined = 对话模式，请求体不带 taskType/text）；新增可选 `docId` 参数（B7 协议） |
| `store/useNoteStore.ts` | + `AiAskType`（explain/translate/summarize）、`AiTask`、`aiTask`、`prefillAiTask`/`clearAiTask`；删除 F5 的 `aiPrefill` 通道（被 aiTask 完全替代） |
| `components/AIPanel/index.tsx` | 重构：`sendMessage(content, taskType?)`；对话模式注入 `docId = readerId`；顶部上下文指示条（全局/单篇+标题）；`aiTask` 消费自动发送；`noteContext` 从 `activeNoteId:xxx` 占位改为当前笔记标题；任务按钮可取消选中（null = 对话模式） |
| `components/Reader/selection-toolbar.tsx` | 「问 AI」点击展开三子项（解释/翻译/总结/收起） |
| `components/Reader/pdf-reader.tsx` | 工具栏 + 「问 AI」按钮（toggleAiPanel）；`handleAskAi(type)` 走 `prefillAiTask` |

## 关键决策

1. **单篇限定用 `docId = readerId`，不新增状态**：正在阅读的文献就是单篇问答的天然上下文（AIPanel 直接读 `useLiteratureStore.readerId`），阅读器开关自动生效/失效——零同步成本，也避免"文献 A 打开、面板却问文献 B"的错位。
2. **划词提问三子项统一走对话模式**（用户决策）：前端把"请解释/翻译/总结以下内容"注入 user 消息 + 带 `docId`——后端 `TASK_PROMPTS` 只有 summarize/polish/continue，加 explain/translate 要改后端（跨端改动违背分支纪律）；对话模式反而让回答结合当前文献上下文（B7 RAG），效果更好。
3. **任务/对话模式用"任务按钮是否选中"区分**：选中任务 = 任务模式（处理 text，无 RAG）；不选 = 对话问答（RAG）。默认不选——问答成为主模式，符合产品定位。
4. **复用 SSE 打字机零改动**：`fetchAiResponse` 的 SSE 解析、AIPanel 的打字机队列、错误分支全部原样保留，只加参数与入口。
5. **noteContext 占位清理**：B7 会把 `noteContext` 注入 system prompt，F5 传的 `activeNoteId:xxx` 是无效占位——改为当前笔记标题（无则空）。

## 踩坑记录

- **合并 backend 前必须先处理未提交改动**：用户写 B7/B8 时在 backend 分支留有未提交的 B8 工作（main.py 挂 export_api、新文件），直接 checkout frontend 再 merge 会因"本地改动将被 merge 覆盖"失败——先 `git stash push -u`（含 untracked）暂存用户工作，切 frontend 合并，之后用户切回 backend `git stash pop` 恢复。
- **双后端进程端口冲突（RAG 不生效）**：用户报"划词问 AI 不检索文献"。排查：前端请求链路、`kb.retrieve`、`build_rag_context`、`_build_messages` 单独测全部正常，但 chat 接口无 RAG——`netstat` 发现 3001 被**两个进程**监听（127.0.0.1 的旧进程 + 0.0.0.0 的新进程），浏览器 `localhost` 命中绑定更具体的旧进程（B7 前的代码）。修复：杀旧进程。教训：**"单独测底层函数正常 ≠ 线上链路正常"**，先确认"进程加载的代码 == 磁盘代码"（对比进程启动时间 vs 代码修改时间）。
- **划词问 AI 来源页码与划词页码不一致**：用户在第 3 页划词，AI 来源标注第 6 页。根因：划词页码（前端 text layer 记录）正确，但划词文本仅作为检索 query，RAG 命中 top-5 chunk（含第 6 页消融实验），AI 引用命中页——且 `prefillAiTask(type, text)` 丢弃了 `selection.pageNumber`，AI 根本不知道出处。修复（用户决策"带出处信息"）：`AiTask` 增加 `pageNumber`/`docTitle`，`handleAskAi` 传入，AIPanel 拼进提问消息 `（出自《标题》第 N 页）`——AI 回答明确标注划词出处。教训：**划词问答是"处理选中内容"，出处（文献+页码）应随消息传给模型**（与转笔记引用 F5 带页码同理），而不是只把文本当检索 query。
